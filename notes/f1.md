# Phase F1 — declaration-stable frontend output

Research notes per `JIT_IMPL.md`'s "Execution rules for agents" rule 3.
Worktree branch `jit/f1`, forked from `fast-devloop` (`547d193c`).
nativenif is the pinned clone at `/Users/chanc/Projects/nativenif`, untouched.

The phase has two halves, both prerequisites of B3b (`notes/b3b.md` §7):

1. number a local symbol inside its enclosing routine instead of from a
   module-wide counter, so an edit to one declaration cannot rename another
   declaration's locals;
2. give hexer a declaration identity that is blind to line info, plus a
   re-base helper for a spliced fragment, so an edit that only shifts lines
   cannot invalidate a declaration either.

## 2. What NIF allows a local symbol to look like

There is no vendored copy of `nifspec` in this checkout; the enforceable rules
live in `src/lib/nifreader.nim`, `src/lib/nifbuilder.nim` and
`src/lib/symparser.nim`, and the prose that exists is
`doc/internals/leng-spec.md:24-30` ("a NIF symbol has the form
`identifier.<number>.modulesuffix` … or `identifier.<number>` for a local
symbol") plus `symparser.derivedName`'s docstring, which quotes nif-spec.md's
global forms `<ident>.<disamb>.<moduleSuffix>` and
`<ident>.<disamb>.<key>.<moduleSuffix>`.

Rules that actually bind, with the code that enforces them:

* **Lexical.** `'.'` is not a control character (`nifbuilder.nim:23`); a
  Symbol token is one run of non-control, non-whitespace bytes. Only the
  FIRST byte is escaped when it is a digit / `.` / `+` / `-` / `~`
  (`nifbuilder.nim:196,216`). Backtick and underscore are legal, unescaped,
  anywhere after the first byte — `symparser.derivedName` already ships
  `` outer`env.0 `` and `intramodinliner.freshSym` already ships `x.0h37`.
* **Local vs global is a DOT COUNT.** `symparser.isLocalName` counts dots and
  answers `dots <= 1`; `nifbuilder.addSymbolDefRetIsGlobal` (the writer's own
  classifier, `nifbuilder.nim:246-254`) answers `dots >= 2`. A name with two
  dots is indexed by `nifcoreparse.emitValueIndexed` into the module's
  `(.index …)`, and `programs.tryLoadSym` will try to `load()` its last
  segment as a MODULE SUFFIX. So **a local must contain at most one dot.**
  This rules out any spelling that puts the owner in a dotted segment of its
  own (`x.0.owner` is a global named `x.0` in a module called `owner`).
* **The single dot must be followed by a digit.** Every `symparser` scanner
  (`extractBasename`, `extractModule`, `splitSymName`, `removeModule`,
  `isInstantiation`) walks backwards for the first dot whose next byte is a
  digit and treats any other dot as a module separator. After that leading
  digit the disambiguator may hold anything lexically legal.
* **Trailing dots** are the module-suffix expansion the NIF API performs
  (`nifreader.nim:189-198,463-464`); nothing here mints one, and a local name
  must not end in `.` — AGENTS.md's warning is respected by never touching
  that slot.
* `symparser.splitLocalSymName` is the one place that additionally demands the
  disambiguator be a pure integer. Its only callers are the two ends of the
  plugin gensym protocol (`semos.nim:619`, `plugins.nim:840`); §4 below
  extends it rather than working around it.

## 3. Where uniqueness is required — the consumer, not a guess

Locals never enter an index and are never loaded across modules:
`nifindexes.isImportant` and `nifcoreparse.emitValueIndexed` index only
symbols the writer classifies as global, and `programs.tryLoadSym` gives up
with `LacksModuleName` the moment `extractModule` returns `""`, which it does
for every one-dot name. `dce1`/`dce2` skip locals explicitly
(`dce1.nim:38,68`). So the index, the loader and DCE place **no** constraint
on a local's spelling.

Uniqueness is nevertheless required, because `pool.syms.getOrIncl` interns by
STRING: two locals spelled the same anywhere in one module are literally one
`SymId`. The compiler already knows this —
`src/nimony/sem.nim:3345-3349` picks helper names specifically to avoid it,
and says why: *"`makeLocalSym` only guarantees per-module uniqueness, so
naming this `expectedType` would share its `pool.syms` ID with that parameter
and the borrow check would resolve to the wrong decl."*

The concrete consumer that breaks first is `EContext.hoistedConsts`
(`src/hexer/hexer_context.nim:51`), a `Table[SymId, SymId]` that lives for the
whole module: `lengcgen.trHoistedConst` (`:1016`) records `proc-level const ->
its hoisted module-level name` and `trExpr` (`:1893`) reads it back. Two procs
that each declare `const c = [1, 2, 3]` would, under per-routine numbering
WITHOUT a namespace, both mint `c.0`; the second `trHoistedConst` overwrites
the first entry and the first proc's uses silently resolve to the second
proc's constant. That is a miscompile, not a diagnostic. `TypeCache`
(`typenav.nim:41`) is scoped per proc and would survive; `hoistedConsts` is
not, and neither is any future module-scoped table.

**A per-declaration namespace segment satisfies this**, because it makes the
strings distinct and therefore the `SymId`s distinct — it does not weaken
module-wide uniqueness, it re-derives it from the owner instead of from a
running count.

There is no SHORT encoding that also works. A per-declaration ORDINAL is
position-derived and would shift under exactly the edit this phase is about; a
hash of the owner's name is short but a collision is a silent miscompile and
it destroys the readability that is half the point (`notes/b3b.md` §7: "makes
every `.s.nif` diff readable"). The owner's own name is the only stable,
collision-free, readable key available at mint time.

## 4. The spelling chosen

```
    x.3`semExpr`0
    ^ ^ ^^^^^^^^^
    | |     └── the owner tag: the enclosing routine's module-less symbol
    | |         name (`semExpr.0`) with its dots turned into backticks
    | └── the disambiguator, a per-(name, owner) counter, first byte a digit
    └── the identifier, untouched
```

* one dot → `isLocalName` true, never indexed, `extractModule` returns `""`;
* the byte after the dot is a digit → every `symparser` scanner splits it
  where it always did;
* the tag rides in the DISAMBIGUATOR, after the number, not in the
  identifier. That is the load-bearing half of the choice:
  `symparser.extractBasename` — and therefore `sembasics.symToIdent`, which is
  how a declaration gets back into scope under its source name — still returns
  `x`. Putting the tag in the identifier (`` x`semExpr`0.3 ``, the shape
  `derivedName` uses for a SIBLING declaration) would make `symToIdent` answer
  `` x`semExpr`0 `` and break name lookup, and would make `newSymId` stack a
  second tag onto the first every time a template body is copied;
* the separator is a backtick for the same reason `derivedName` uses one: it
  keeps the result out of the Nim-spellable namespace and out of the dot
  grammar;
* a local with NO enclosing routine — a `var` inside a top-level `if`/`block`
  — keeps today's exact spelling `x.3` and today's module-wide counter. There
  is no owner to name, these are rare, and an appended proc cannot renumber
  them.

The counter is keyed by `identifier`+backtick+`owner tag` in the same
`SemContext.locals` table as before, so it is PERSISTENT per owner rather than
pushed and popped. That matters: a generic instantiation's parameters are
minted twice, once for the signature `requestRoutineInstance` builds for
overload resolution and once for the body `subsGenericProc` emits, and a
counter that restarted at 0 would give both the same names.

`splitLocalSymName` gains a fourth `tail` parameter and the three-argument
form keeps its old meaning (`tail` must be empty), so the plugin gensym
protocol carries the tag across the process boundary unchanged in shape: the
compiler offers `` tmp.7`semExpr`0 ``, the plugin mints
`` tmp.8`semExpr`0 ``, `` tmp.9`semExpr`0 `` and reports the first it did not
use. At module level the tag is empty and the protocol is byte-for-byte what
it was.

### Where the owner is established

| site | owner |
|---|---|
| `semdecls.semProcImpl` (`:1067` / `finally` at `:1184`) | the routine's own `symId`; covers every proc/func/iterator/converter/method/macro/template and every hook, in every pass |
| `sem.subsGenericProc`, `sem.subsGenericType` | `req.targetSym` — the instantiation, not the module that asked for it |
| `sem.requestRoutineInstance` | `targetSym`, for the signature copy |
| `enumtostr.genEnumToStrProc` | the synthesized `dollar`.<Enum>` func |
| everything else (template expansion, `instantiateType`, `instantiateExprIntoBuf`, `bindSubsInvokeArgs`) | inherits the current owner — a template body is emitted into the routine it is expanded IN, so that is the routine its gensyms belong to |

Template expansion deliberately does NOT open a namespace of its own. Two
expansions of one template in two different routines must not share a counter,
or the second routine's names would depend on the first.

### What this phase does NOT make stable

`derefs.nim`'s `` `err.<n> `` (`:1002`) and `controlflow.nim`'s `` `cf.<n> ``
(`:189` …) use their own module-wide counters and bypass `c.locals` entirely.
`injectDerefs` runs once over the finished module, so an inserted proc that
raises renumbers the `` `err `` temps below it. It does not affect the gate's
edit (an appended `proc f(): int = 1` mints none) and it is a much smaller
population; it is recorded here as the next thing to do if the numbers ever
demand it. Hexer's own seven counters (`notes/b3b.md` §2) are B3b's step 3.

## 5. Line info and a blind identity

`NifLineInfo` (`nifcore.nim:246`) is absolute `(file, line, col)` and rides as
a sparse `LineInfoLit` suffix on a head token (`nifcore.nim:204-229`), not as
a field. In TEXT NIF it is the `@col,line,file` / `~col` suffix
(`nifreader.nim:303-378`, `nifbuilder.attachLineInfo:361-393`) and it is
encoded RELATIVE to the enclosing tag's resolved position
(`nifcoreparse.emitRelLineInfo:178-198` and its inverse `resolveInfo:37-55`).
Everything nimony/hexer parse is read with `denseLineInfo = true`, so in
memory every positioned token carries its own suffix.

Nothing in hexer or lengc branches on the VALUE of line info: `dce1` never
reads `.info` at all, `dce2` only re-emits it. The comparisons that exist are
diagnostics bookkeeping (`reporters.reportedErrSources`, `mover`, `lifter`)
plus two real ones outside this phase's path — `templates.nim:180-186`'s
`--inlineframes` decision and `idetools.nim:201`.

**The blind digest already exists.** `src/lib/nifchecksums.nim`'s
`computeChecksum(n: Cursor)` walks a subtree hashing tag names, symbol names
and literal values, and never touches `.info` — `Cursor` navigation classifies
`LineInfoLit` as a suffix (`nifcore.tokenWidth:555-608`) and steps over it. It
had ZERO call sites: every content-addressed cache in the tree
(`deps.nim`, `engine.nim`, `semos.nim`) hashes serialized TEXT, which contains
line info. F1 gives it its first user.

**Re-basing is not a blanket subtree shift.** A declaration's token stream can
carry info from other files: `sem.subs` (`:372-411`) copies a generic body
verbatim, keeping the DECLARING module's file/line on every inner token, and
`templates.nim:196-201` forges a composite filename whose text embeds the
template's declaration LINE (`comesfrom.nim:56-72`). So the rebase must decide
per token, on the token's own `file`, and must leave a foreign or forged file
alone. That is what `rebaseLineInfo` implements.

### Sidecar

`<mod>.decls.nif` is written beside `<mod>.x.nif` and `<mod>.dce.nif` by
`lengcgen.writeExpandResult`, with `nifbuilder.open(..., OnlyIfChanged)` — the
same lightweight, pool-free shape `dce1.writeAnalysis` uses. One entry per
top-level declaration:

```
(decl <symbol> <digest of its .s.nif subtree> <digest of its .x.nif subtree>)
```

Both digests are line-info-blind. `.x.nif` itself is untouched — P0c's
byte-identity depends on it and the sidecar is a third output, not a change to
the second.

### Corrections to `notes/b3b.md`

That note's "49 blind" for the two-statement insertion was a measurement
error, not a compiler property. The scenario's textual stripper removed `@…`
suffixes only, and `nifbuilder.attachLineInfo` omits the `@` when the column
diff is negative because the leading `~` already carries the sign — a suffix
can read `~C,~1Ib` with no `@` in it, and the base-62 line delta left behind
read as content. With both openers stripped the fork point already reports 1,
and hexer's token-stream digest agrees. What F1 changes about that edit is
nothing; what it changes is the appended-proc edit.

Its `EContext.hoistedConsts` claim is the other correction, in the other
direction: `notes/b3b.md` did not name a consumer that requires module-wide
uniqueness of local names, and this note does (section 3). Numbering per
routine WITHOUT the namespace segment would have been a miscompile, not a
cosmetic change.

### What it costs

The whole nimcache of a self-compile: `.s.nif` +34.9 %, `.x.nif` +30.6 %,
plus a 2.0 MB `.decls.nif` set that did not exist. sem's own `.s.nif` goes
3.30 MB → 4.33 MB. That is the price of writing the owner's name into every
local, and section 3 argues there is no shorter encoding that is also stable.
The token COUNT and the dot-count histogram of sem's `.s.nif` are unchanged,
which is the check that nothing was reclassified from local to global.

### 8.1 A diagnostic names a symbol by the identifier the user wrote

F1's own golden commit (`cabb76c0`) argued for the change with this pair:

```
before   Error: borrow of 'a.6' escapes its scope
after    Error: borrow of 'a.0`escapeViaBlock`0' escapes its scope
```

The second is better than the first — it says WHICH `a` — but the user never
wrote either. The nine `a`s of `topenarray_escape_errors.nim` are nine
different `a`s in nine different procs, and the message already tells them
apart: it opens with `topenarray_escape_errors.nim(68, 13)`. The internal
counter never disambiguated anything the location did not.

**The rule.** A message that names a symbol renders `symparser.sourceIdent`:
the identifier, with the disambiguating count, the F1 namespace segment and
the module suffix all dropped. Disambiguation is the message's own
file/line/column. There is one helper each side of the `SymId`:

* `symparser.sourceIdent(name: string)` — the string form, so `macro_plugin`
  and anything else without the renderer can use it. It wraps the IN-PLACE
  `extractBasename`, which leaves a name with no `.<digit>` alone; the
  string-returning overload answers `""` for those, and `undeclared identifier:
  T` prints exactly such a name.
* `renderer.asNimSym(symId: SymId)` — the `SymId` form, next to `asNimCode`.
  `sem.nim` already had a private copy of exactly this and used it for the
  object-construction messages; that copy is gone and the export took its
  place. `macro_plugin.cleanSymbolName` was a third, cruder copy (first dot
  rather than the first dot followed by a digit) and is gone too.

Call sites moved: `contracts.nim` (1), `contracts_fir.nim` (7 — the borrow and
init-proof messages), `expreval.nim` (1), `sem.nim` (2), `semcall.nim` (1),
`semmain.nim` (2), `semtypes.nim` (1), `sigmatch.nim` (3).

**Two families deliberately keep the full symbol.**

* `could not load symbol: <sym>; errorCode: <status>` (`sem.nim:1938`,
  `semcall.nim:19,267`) and the `bug`/`assert` texts in `sizeof`, `typenav`,
  `typeprops`. These report that the COMPILER could not find something; the
  module suffix is the content of the message, not noise around it.
* `idetools.foundSymbol`. Its own comment says the format "is compatible with
  nimsuggest's" — it is a machine protocol whose symbol column IS the symbol's
  identity, and `tests/nimony/track/tproc.msgs` already carries a full
  `add.0.tpr9d7lx31` for a global. Stripping locals there and not globals would
  be inconsistent, and stripping both would make two `use` lines for two
  different `x`s indistinguishable to the editor. `tvar.msgs` therefore still
  reads `x.0`main`0` and that is not an oversight.

### 8.2 The last two module-wide counters

`derefs.nim`'s `` `err.<n> `` and `controlflow.nim`'s `` `cf.<n> `` now key on
the same namespace segment `makeLocalSym` uses, through the shared
`symparser.localNamespace` (`sembasics.localNamespaceOf` is now one line over
it):

```
   `err.0`guardedVoid`0        derefs.nim,      per enclosing routine
   `cf.0`step6`0               controlflow.nim, per routine the graph is built for
```

`` `err `` was the real one. Its counter lived on the module-lifetime `Context`
`injectDerefs` builds once per module, and its names go into the `.s.nif`, so a
proc inserted above a `try`/`except` renumbered every later handler's `err`.
Measured on a two-handler module at the fork point:

```
before   `err.1   `err.2
after    `err.0`guardedVoid`0   `err.0`guardedVoid2`0
```

The counter is a `Table[string, int]` keyed on the namespace rather than a
field reset on routine entry, for the reason §4 gives for `c.locals`: a keyed
counter cannot hand two passes over one routine the same name.

`` `cf `` was not: `toControlflowImpl` builds a fresh `ControlFlow` per routine,
so `nextVar` already restarted, and the graph is an analysis IR that is thrown
away — no `` `cf `` reaches any artifact (grep of a full nimcache confirms).
§4's "module-wide counters" is wrong about it. It is namespaced anyway, because
§3's `hoistedConsts` argument is about `SymId` identity and `pool.syms` interns
by STRING: two routines that each mint `` `cf.0 `` are literally one `SymId`
today, and any future module-lifetime table keyed on one would silently merge
them. `tests/controlflow/*.expected.nif` do not move — every fixture there is a
module-level `(stmts ...)`, where the namespace is empty and the spelling is
byte-for-byte what it was.

No other counter mints a name. `grep -n 'Count\|counter' src/nimony/*.nim`
turns up `semdata.templateInstCounter` (a recursion depth, not a name),
`exprexec.generateName` (keyed on a type key, in a synthesized sub-module),
`makeFieldSym` (per type since the `fieldCounts` fix) and `makeGlobalSym`,
whose number IS a top-level declaration's identity and cannot be scoped to
anything smaller. Hexer's seven are B3b's step 3.

### 8.3 What the scenario now measures

`tests/incremental/b3b_lib.nim` gains a ref-exception type, a raising helper,
two procs that catch it (`guardOne`, `guardTwo`) and one with a `while` over a
`case` (`loopOne`), all below the insertion point — the only position where a
module-wide counter shows. The `insert` edit correspondingly inserts a second
proc that catches, so there is something to renumber, and the blind bound drops
from `<= 2` to `<= 1`.

```
before (fork point, old fixture)
  decl-stability: .s.nif 13 decls | in-place changed 1 | insert changed 7 (blind 1, added 1) | stmtadd changed 8 (blind 1) | decls digest 23 syms, changed 1/0/1 | .x.nif in-place changed 1

after (new fixture, this branch)
  decl-stability: .s.nif 32 decls | in-place changed 1 | insert changed 11 (blind 1, added 2) | stmtadd changed 12 (blind 1) | decls digest 52 syms, changed 1/0/1 | .x.nif in-place changed 1

the new fixture against the fork-point compiler, i.e. what the extension buys
  decl-stability: .s.nif 32 decls | in-place changed 1 | insert changed 11 (blind 3, added 2) | stmtadd changed 12 (blind 1) | decls digest 52 syms, changed 1/2/1
  decl-stability: insert: 3 of 32 declarations changed with line info ignored (expected at most 1)
```

The two extra declarations are `guardOne` and `guardTwo`, whose `` `err `` the
inserted proc renumbered. That is the whole of §8.2 in one line.

The `guard*` procs return nothing, which breaks the fixture's "every proc
returns a value" rule on purpose: a value-returning proc whose body catches a
ref exception does not survive the C backend (`error: non-void function ...
should return a value` on the error-propagation path). Reproduced at the fork
point with the stashed sources, so it is not this branch's; recorded here
because the next person to touch this fixture will hit it.
