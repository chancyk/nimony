## 2. Why the counters reach both ways along the module

Every pass in `pipeline.transform` builds ONE context per module and walks the
whole buffer with it, and the temp counter lives on that context. That alone
would only let an edit renumber the declarations BELOW it. Two things carry it
upward as well:

* `Pass.nextTemp` was threaded from pass to pass (`passes.nim:21`,
  `xelim.nim:1521,1531`), and `lowerExprs` runs over the whole buffer more
  than once — `xelim1` and `xelim_final` in `pipeline.transform`, plus one
  nested Final-IR run per coroutine in `coro_transform.treIteratorBody`. The
  temps the first declaration receives on the SECOND run are numbered from
  where the FIRST run left off, i.e. from what the LAST declaration needed.
  `xelim.nim:1515`'s own comment says a counter that restarted would collide;
  what it did not say is what threading costs.
* `intramodinliner.intraModuleInline` walks the module once with one
  `InlinerCtx`, so the names of the locals a splice brings into a proc depend
  on how many splices happened in the procs before it.

Both are visible in the diff of a proc the edit does not touch:

```
-   (var :`x.840 . xint.0.xincut4p51        +   (var :`x.841 . …
-    (var :t.0h65 .                         +    (var :t.0h91 .
-     (lab :returnLabel.0h74)               +     (lab :returnLabel.0h100)
```

## 3. The fix, and why it is F1's

There are two ways to make a declaration's names independent of the module:
CHECKPOINT every counter (and every module-wide table) at each declaration
boundary and restore it in both directions, or DERIVE the name from the
declaration instead of from a running count. `notes/b3b.md` §11 argued the
first is a miscompile waiting to happen — a mistake in any one of the seven
counters plus `hoistedConsts`, `pending`, `strLits`, `newTypes`, `initBody`
and the two hook tables is two declarations minting the same `` `x.N ``, which
`pool.syms.getOrIncl` interns to ONE `SymId`. F1 §3 made the same argument and
chose the second. So does this.

### The spelling

Exactly F1's (`notes/f1.md` §4), one level down:

```
    `x.3`semStmt`0
    ^^ ^ ^^^^^^^^^
    |  |     └── the owner tag: the enclosing declaration's module-less symbol
    |  |         name (`semStmt.0`) with its dots written as backticks
    |  └── the disambiguator, a per-(name, owner) counter, first byte a digit
    └── the identifier, untouched
```

* one dot → `symparser.isLocalName` true, never indexed, `extractModule`
  returns `""`;
* the byte after the dot is a digit → every `symparser` scanner splits it
  where it always did, and `extractBasename` still answers `` `x ``;
* the separator is `symparser.LocalNsSep`, the backtick F1 introduced.

A GLOBAL-layout name keeps the module suffix as its LAST dotted segment, so
the dot count is still two and nothing is reclassified:

```
    `setlit.0`semStmt`0.mymod
```

`extractModule` finds `mymod` (the byte after that dot is not a digit),
`extractBasename` finds `` `setlit `` (the byte after the other dot is), and
`isInstantiation` still says no. The three synthesized-global families that go
through this are `` `setlit ``, `anonArr`, the `` `iterFrame ``/`` `iterVal ``/
`` `coroIt ``/`` `coroEnv ``/`` `thisReuse ``/`´cont` set, the closure env
FIELDS (`` x`f.0`outer`0.mymod ``) and the consts hoisted out of proc bodies.

A declaration with no name — a bare top-level statement, i.e. module init code
— gets the empty namespace and keeps today's exact spelling and today's
module-wide counter. There is no identity there to be stable for, and every
one of those statements lands in the same `c.initBody` anyway.

### The counter is persistent per owner, not pushed and popped

This is the load-bearing half. `lowerExprs` visits the same routine more than
once and the second visit sees the temps the first one declared; a counter
that restarted at 0 for that owner would re-mint names that are still live in
the same proc — one frame slot, two types, which is
`tests/nimony/cps/tifexpr_arg_temp_collision.nim`. So the counter is a
`Table[identifier + namespace, int]` that lives as long as the module, exactly
like F1's `SemContext.locals`. Scoping is done by the KEY, not by resetting.

### Where it lives

`passes.TempNamer` (`ns` + the table) with `freshName`/`freshSym`/
`freshGlobalName`/`freshGlobalSym`/`namespacedName`, and
`passes.localNamespaceOf` / `passes.toplevelNamespace` to derive `ns`.

Two instances, because the pipeline is not the whole of hexer:

* `Pass.namer` — the eleven pipeline passes. Each pass `swap`s it into its own
  context at entry and back out at exit, which is O(1) and is the same in/out
  idiom `Pass.nextTemp` already had. The nested per-coroutine Final-IR run
  swaps its owner's namer in rather than seeding an integer, so its counters
  continue exactly as before.
* `EContext.namer` — `elimForLoops`, which runs BEFORE the pipeline, and
  `lengcgen`/`stringcases`, which run after it. `EContext` is the one object
  that spans all three.

`ns` is set where each walker enters a declaration:

| pass | where | owner |
|---|---|---|
| `iterinliner.transformStmt` | the `FuncS, ProcS, ConverterS, MethodS` and `IteratorS` branches | the routine (this replaces the `e.tmpId = 0` save/restore that was already there) |
| `desugar.trProc` | around `trProcBody` | the routine |
| `lambdalifting.trProc` / `trIterDecl` / `treProc` | at the LIFTING ROOT (`procStack.len == 0`) | the root routine — a nested proc's temps belong to the top-level declaration the whole nest came from |
| `coro_transform.transformCoroutineDecl` | around the whole decl, helpers included | the coroutine |
| `xelim.trProc`, `duplifier.trProcDecl`, `vtables_backend.trProcDecl` | around the body | the routine |
| `lengcgen.trToplevel` | per top-level statement | `toplevelNamespace`: the statement's own `SymbolDef`, or empty |
| `intramodinliner.intraModuleInline` | per inlinable top-level proc | the proc being rewritten (`counter` restarts, the namespace is what keeps the names unique) |

### What needed nothing

`eraiser` and `constparams` build a FRESH `Context` per routine already
(`eraiser.nim:499`, `constparams.nim:102`) and carry only the type cache back
out, so their counters restarted per declaration before this phase.
`coro_transform.ProcContext` was swapped per decl for the same reason; its
names went through the namer anyway, because `cps.nim` reads that same
`currentProc.counter` for `` `contVar ``/`` `coroVar `` at call sites that are
NOT inside `transformCoroutineDecl`'s swap. `destroyer` has no counter — its
one synthesized name is the constant `` `anonblock.0 ``.

## 4. What still needs module-wide uniqueness, and why the namespace gives it

Scoping by KEY does not weaken uniqueness — it re-derives it from the owner
instead of from a running count — so every module-wide consumer keeps working.
The ones that would have broken under a plain per-declaration RESET, and are
therefore the reason the namespace exists:

* **`EContext.hoistedConsts`** (`hexer_context.nim`, written
  `lengcgen.trHoistedConst`, read `trExpr`) — `Table[SymId, SymId]` from a
  proc-level const to its hoisted module-level name, live for the whole
  module. Two procs that each declare `const c = [1,2,3]` must not both mint
  `c.0.mymod`. F1 §3 named this one; it is now `` c.0`f`0.mymod `` and
  `` c.0`g`0.mymod ``. The `localDeclCounters: 1000` seed that used to keep
  these away from real module-level names is gone with the counter.
* **`lambdalifting.envFieldType`** (`Table[SymId, Cursor]`, env FIELD sym →
  the captured local's type) — its own comment said the table was "safely
  module-wide" *because* the field syms were counter-minted per module. The
  namespace is what replaces that guarantee.
* **`desugar.hoisted`** — the module-level `const`s minted for set literals,
  emitted once as a block ahead of the module body. Same shape as
  `hoistedConsts`, one buffer instead of a table.
* **`lifter.hookNames`** stays module-wide and untouched: a hook is named from
  the TYPE key it was derived from (`=destroy_<key>.<n>.<mod>`), which is
  content-addressed and shared by every use of that type across the module. It
  is not a temp and it has no owning declaration.
* **`EContext.strLits` / `newTypes`** stay content-addressed
  (`strlit.0.I<hash>.<mod>`, `genericTypeName`). `lengcgen.nim:1301` already
  explains why a counter was rejected there, and the same reasoning applies to
  everything else that has to mean the same thing in two modules.
* **`c.initBody`, `c.pending`, `c.dynlibs`** are one buffer/list for the whole
  module by construction. Their ORDER is still declaration order; nothing here
  changes that, and B3b's splice will have to treat them as whole-module
  output regardless.

### `src/nimony/sem.nim`, the `grow` edit

| | sem-input | lowering-output |

| after | 1 of 1785 | **3** of 1785 |

(`notes/b3b.md` §11 recorded 890 of 1794 for the same edit on the F1 tip; the

The three are `semStmt` itself and the two procs `intraModuleInline` splices

and it is exactly the dependency `notes/b3b.md` §14's step 6 will have to
model with an inline map.

### What did NOT move, and why

The raw BYTE churn of the same artifacts, split textually (the method of
`notes/b3b.md` §3, which keeps line info) on the same edit:

| artifact | before | after |
|---|---|---|
| `.x.nif` | 1148 of 1753 | 525 of 1753 |
| `.c.nif` | 632 of 974 | 452 of 974 |
| `.asm.nif` | 460 of 975 | 434 of 975 |

Those numbers are dominated by something F2 does not own: an inserted LINE
renumbers every `@…` below it in the file, so every declaration after the edit
point differs textually whatever its symbols are called. That is the reason
F1 built a line-info-blind digest in the first place, and it is why the
sidecar's 3 — not the 525 — is the number a declaration-level splice consults.
The `.asm.nif` column moves least because arkham names its own temps from the
ABSOLUTE TOKEN POSITION in its input (`aggtmp<pos>`, `nctmp<pos>`, …), so any
size change upstream renames them; that is `notes/b3b.md` §14's step 5 and it
is in nativenif, not here.

nifasm's blob-cache counters on the same edit, `NIFASM_PROFILE=1`, before and
after F2:

```
before:  blobHits 3415   blobStale 18   blobRecorded 627
after:   blobHits 3415   blobStale 18   blobRecorded 627
```

Identical, and that is the expected result rather than a disappointment:
`blobcache.sameSource` validates a fragment against its MODULE's `.asm.nif`
stamp, so sem's file changing at all still drops every fragment whose symbol
lives in sem. F2 changes how MUCH of that file changes, not how the check is
made. `notes/b3b.md` §12 priced per-symbol validity at 627 → ~467 before this
phase and ~2 after §14's step 3; this measurement is the "before §14 step 4"
half of that, and the reason step 4 is now worth ~180 ms instead of ~55.

### Determinism (P0c)

The 127-module compiler built twice into two fresh nimcaches from identical
sources: **381 artifacts compared, 0 differ** (127 each of `.x.nif`,
`.dce.nif`, `.decls.nif`).

### Cost

The names carry their owner, so the artifacts grow: sem's `.x.nif` 6.29 MB →
8.05 MB (+28.0 %); its `.decls.nif` is unchanged at 430 kB, because the sidecar
holds digests, not names. F1 paid +30.6 % on `.x.nif` for the same reason one
level up. That is the price of writing the owner's name into every temporary,
and §3 argues there is no shorter encoding that is also stable.

## 7. Risks and what is left

* The names are longer. A deeply nested generic instantiation's routine name
  is already long, and a temp inside it now carries the whole thing. This is
  the same trade F1 made and the same answer: a hash would be shorter, and a
  collision in it is a silent miscompile.
* `.x.nif` byte-identity against the fork point is GONE by construction — this
  phase renames symbols. That is the one thing P0c's determinism check cannot
  cover, and the goldens diff is what covers it instead.
* `intraModuleInline`'s three-declaration answer is the floor for the sem
  measurement until the inline dependency map exists. An edit to a widely
  `.inline`d proc will still touch every caller, correctly.
* Top-level statements (module init code) still share one module-wide counter
  under the empty namespace. They also share one `initBody`, so a
  declaration-level splice cannot treat them separately anyway; if that ever
  changes, this is the next thing to scope.
* `vtables_backend` routes `IteratorS` through its pass-through branch rather
  than `trProcDecl`, so a `` `vtableTemp `` minted for a method call inside a
  concrete `.closure` iterator body still gets the enclosing namespace instead
  of the iterator's. It is the one residual position dependence found; it does
  not show up in either measurement and routing iterators through
  `trProcDecl` there is a behaviour change (it would take the routine header),
  so it is recorded rather than done.
* `tests/nativecg/tinlinecond.x64.asm.nif` is stale and this branch cannot fix
  it — see §6. Whoever next runs the suite on x64 regenerates it, and the diff
  they see will be larger than F2's because the golden already predates F1.

## 8. What B3b can now do

Both halves of the sidecar are declaration-local, so the pair
(input digest, output digest) means what step 1 of `notes/b3b.md` §14 needs it
to mean: the input digest decides what to re-lower and the output digest
decides what may be spliced, and an unchanged declaration's output really is
byte-identical. The remaining items on that list are unchanged:
nifasm's per-symbol blob validity (§12: 627 recorded → ~2 now that hexer's
output no longer churns), arkham's per-proc splicing, and the incremental
`expand` itself — whose floor `notes/b3b.md` §10 puts at 112 ms unless
`funcsummary`, `intraModuleInline` and the serialize are made incremental too.
