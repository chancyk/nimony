# M1 — memory in the cost ledger and the scheduler

Motivation: `bench/results/2026-09-07/progress.md` run 10. The in-process
scheduler raises the largest process of a cold self-compilation from 147 MB
(everything spawned) to 215 MB, against 116 MB at the fork point. The edit
loop and CTFE are unchanged. `doc/design.md`'s "low memory consumption" goal
and JIT.md 5.2 say that decision has to be *measured* and *overridable*, like
the spawn decision it sits beside.

## 2. The dual-dialect constraint

`src/lib/ledger.nim` is compiled by nimony in `hastur boot` (it reaches the
booted compiler through `deps.nim`). `src/nimony/phases.nim` and
`src/nifmake/dag.nim` are **not**: `nimony.nim` imports `phases` under
`when not defined(nimony)`.

Consequence for this phase: only `peakRssBytes()` has to exist in both
dialects. It is written with the constructs `lib/std/cpuinfo.nim` already
proves nimony accepts — `importc` + `header:`, a plain object laid out by
hand, `cast[pointer](addr x)` — and every branch answers `0` rather than
raising when the platform does not say. Physical memory and the budget rule
live in `phases.nim`, which is host-Nim only, so they cost no dialect risk at
all.

## 3. Design

### 3.1 The sample

`LedgerSample` gains

```nim
rssBytes*: int64   ## peak resident size of the process that took the sample
rssInproc*: bool   ## that peak is the DRIVER's, not the phase's own
```

read once in `PhaseTimer.finish` from `getrusage(RUSAGE_SELF).ru_maxrss`
(bytes on macOS, KiB on Linux) or `GetProcessMemoryInfo.PeakWorkingSetSize`
on Windows. One syscall per tool run, no sampling thread.

The peak is monotone — a process cannot un-touch a page — which is what makes
it affordable and what makes the two kinds of sample different in kind:

* a spawned tool's peak *is* the phase's footprint; the process did nothing
  else;
* the driver's peak while an in-process node ran is the high-water mark of an
  address space that also holds the build graph, the artifact store and the
  allocator's leftovers from every earlier node.

So `LedgerEntry` keeps them in two averages, `ewma.rssBytes` (spawned) and
`rssInprocBytes` (in-process), written as `(rss bytes N)` and
`(rssinproc bytes N)`. `estimate` answers with the spawned one when there is
one and falls back to the in-process one otherwise, which is deliberately the
conservative direction: a phase that has only ever run in-process is estimated
at the whole driver's peak, and the memory rule then keeps it out until there
is a real measurement to replace the guess.

Both averages seed on their first observation instead of blending against 0
(the argument `foldSpawn` already makes for `spawn`): a build is not run
often enough for a factor-of-three cold start to wash out.

### 3.2 The rule

```
in-process is declined when   driverPeakNow + max(est. rss of the depth's
                              registered nodes)  >  budget
```

`driverPeakNow` is `getrusage(RUSAGE_SELF)`, i.e. the peak so far rather than
the resident size right now. That is the cheap number, it is monotone, and it
is the right one for the question: what the process has already touched is
what it will still be holding at the allocator level when the next node runs.

The default budget:

```
budget = clamp(physicalMemory / (8 * cores), 128 MB, 1 GB)
```

Story: a build's steady state is `cores` tool processes at once; the share of
the machine the compiler is willing to occupy is an eighth of physical memory;
the in-process driver stands in for *one* of those processes, so its share of
that share is `physical / (8 * cores)`. The floor of 128 MB is below what a
single large `nimsem` needs, so the rule can never make a build impossible;
the ceiling of 1 GB stops a machine with a terabyte of RAM from meaning "no
limit". On the benchmark machine (16 GiB, 10 cores) that is 204 MB.

Overridable exactly the way the spawn decision is: `--inproc-mem-budget:<MB>`
on the command line, `NIMONY_INPROC_MEM_BUDGET` in the environment (which is
how it reaches a nested `nimony s`), `0` to switch the rule off entirely.
`--spawn:always` and `--vfs:disk` still force spawning; the wall-time rule is
untouched.

Unlike the wall-time rule, the memory rule is asked of **every** node,
including a depth of one. It is a safety valve rather than a trade, and a
single 200 MB `nimsem` is exactly the node that has to be allowed to leave.

### 3.3 Reporting

* `--stats` gains a `peak MB` column (the max over the phase's keys — the
  largest module is what the scheduler has to fit) and a `[stats] driver`
  line with the driver's own peak. Both are produced by `ledger.statsTable`,
  so `deps.nim` needs no hunk.
* `NIMONY_PROFILE_NODES=1` in-process lines gain `rss=+N.NMB`, the driver
  peak's delta across the node; spawned lines gain `childpeak=N.NMB`,
  `getrusage(RUSAGE_CHILDREN)`'s running high-water mark, which is one
  syscall and is the largest child seen so far rather than this one's.

## 4. Risks

1. **The estimate is a peak, not a footprint.** Adding `driverPeak` and a
   node's own peak double-counts everything both processes touch (the pools,
   the parsed input). The rule is therefore conservative by construction. It
   is a safety valve, so that is the right direction, but it means the budget
   number is not "megabytes the build will use".
2. **`openLedger` on a path that used to skip it.** A single-node depth
   answered `true` without reading the ledger; the memory rule needs an
   estimate, so it now folds the fragments (9.6 ms on a 127-module nimcache).
   Mitigated by answering "decline" without the ledger when the driver's peak
   alone already exceeds the budget, and by the fact that a no-change build
   still offers no node at all.
3. **A feedback loop, on purpose.** A phase pushed out to a process records a
   smaller (own) peak, which may let it back in-process, which grows the
   driver again. That oscillation is the rule holding the driver near the
   budget rather than a bug — but it does mean a build's schedule is not
   reproducible from its inputs alone. `--spawn:always` and an explicit
   `--inproc-mem-budget` are the reproducible settings.
4. **32-bit.** The hand-laid `struct rusage` is the LP64 layout. The code
   checks `sizeof(clong) == 8` at run time and answers 0 otherwise; 0 means
   "this platform does not say", which every reader treats as "do not decide
   on memory".
