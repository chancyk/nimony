# Phase H1 — an incremental whole-program live set in hexer

Research notes written before the implementation (`JIT_IMPL.md`, "Execution
rules for agents", rule 3). Worktree branch `jit/h1`, forked from
`fast-devloop` (`55c0521e`, i.e. with P0a–P0c, A1a–A1d, A2a×3, A2b, A2c, B2,
B3b, B3c, B3d, F1, F2 and M1 already in). Machine: macOS 26, arm64, Nim
2.2.10.

Owner files: `src/hexer/dce1.nim`, `src/hexer/dce2.nim`, `src/hexer/hexer.nim`
(`dl`), the `dceLive` node emission in `src/nimony/deps.nim`,
`tests/incremental/**`, a scenario proc in `src/hastur/incrementaltests.nim`,
this file, `bench/results/2026-09-07/h1.txt`.

**The phase did not need the mechanism it was scoped for.** The measurement
below says `dceLive`'s 0.36 s was not the cost of the whole-program
recomputation. It was an accidental deep copy inside the fixpoint loop.
Removing it makes the stage 0.05 s with byte-identical output, which clears
the 0.08 s gate with room to spare, so no incremental live set was built.
Section 4 records what an incremental version would still have to do, and why
it is now worth less than it costs.

---

## 1. The measurement

`dceLive` was re-measured stage by stage before anything was changed, with a
standalone harness over the self-compilation's real inputs (131 `.dce.nif`
analyses, 3.1 MB, from a cold `nimony n` of `src/nimony/nimony.nim`). The
harness calls the same `dce1`/`dce2` procs the `dl` sub-command calls and
times the stages apart. Median of three runs, in milliseconds:

| stage | before | after |
|---|---|---|
| read + parse the 131 `.dce.nif` | 18.9 | 18.6 |
| build the `Table[string, ModuleAnalysis]` | 6.5 | 6.6 |
| `resolveSymbolConflicts` | 1.2 | 1.3 |
| **`markLive` (the worklist fixpoint)** | **311.6** | **7.2** |
| write `<main>.all.live.nif` (the anchor) | 2.9 | 2.9 |
| write the 131 per-module `<M>.live.nif` | 14.4 | 14.2 |
| **total** | **355.8** | **50.8** |

And the real binary, `hexer dl --split:…` with the exact argv the build graph
emits, five runs each after a warm-up:

```
PRE-FIX   real 0.70 (cold) 0.36 0.36 0.35 0.36
POST-FIX  real 0.05        0.05 0.05 0.05 0.05
```

The graph it walks is small: **7867 worklist pops**, 53674 dependency visits,
61541 `translate` calls, 20 roots, 17328 `uses` owners, 103027 edges, 11360
offers, 4646 resolve entries, 6773 live symbols. 311 ms for 7867 pops is
40 µs per pop — three orders of magnitude off what a hash lookup plus a set
insert costs. That ratio is what pointed at the copy rather than at the
algorithm.

### The cause

`src/lib/compat2.nim` gives `getOrQuit` two host-Nim overloads:

```nim
proc getOrQuit*[A, B](t: var Table[A, B]; k: A): var B    # mutable receiver
proc getOrQuit*[A, B](t: Table[A, B]; k: A): B            # returns BY VALUE
```

`markLive` took `moduleGraphs` as a non-`var` parameter, so every lookup in
the loop bound the second overload and the binding

```nim
        let graph = moduleGraphs.getOrQuit(moduleName)
```

materialized a **full copy of a whole `ModuleAnalysis`** — a
`Table[SymId, HashSet[SymId]]` plus two `HashSet`s, thousands of entries for a
module like `sem` — on **every worklist pop**. The line below it,
`for dep in graph.uses.getOrQuit(sym)`, copied the dependency `HashSet` on top
of that, because `graph` is a `let` and so takes the by-value overload again.

The fixpoint itself is 7 ms. The other 305 ms was copying data structures in
order to read one field of them.

Nimony's own `getOrQuit` (`lib/std/tables.nim:79`) is
`func getOrQuit*[K: Keyable, V](t: Table[K, V]; k: K): var V` — one overload,
returning `var V` — but `let graph = …` materializes a copy there too, so the
same waste was present in the self-hosted build.

### The fix

Take `moduleGraphs` as `var` and never materialize the intermediate:

```nim
        if moduleGraphs.getOrQuit(moduleName).uses.hasKey(sym):
          for dep in moduleGraphs.getOrQuit(moduleName).uses.getOrQuit(sym):
```

With a `var` receiver both lookups bind the `var B` overload, so nothing is
copied; the second `getOrQuit(moduleName)` is one extra hash lookup per pop
(7867 of them, unmeasurable). Both callers — `computeLiveSet` and
`deadCodeElimination` — already hold their table in a `var`, so no call site
moved. The comment above the proc records why the shape is what it is, because
the obvious "tidy" rewrite back to a `let` binding silently costs 305 ms.

## 2. Byte-identity

`markLive` is a pure function of `(moduleGraphs, resolved)` and the change
only removes copies, so the result must be identical. Checked rather than
argued, three ways:

1. In the harness, the old and new `markLive` were run back to back over the
   same 131 analyses in one process and their `Table[string, HashSet[SymId]]`
   results compared key by key: **identical**.
2. `hexer dl --split:` was run over the same inputs by a pre-fix binary and by
   the fixed one, into two clean directories, and the directories compared
   with `diff -r`: **all 131 `<M>.live.nif` plus `<main>.all.live.nif`
   byte-for-byte equal** (1.8 MB each side). The only file that differs is the
   ledger fragment `.ledger/dceLive_.nif`, and only in its timings —
   `(produce ns 314761333)` against `(produce ns 17471792)`, which is the
   measurement itself.
3. The suites in section 5, including `hastur boot --boot-backend:native`,
   whose stages are byte-identical.

## 2a. Where it lands in a build, and why the A/B median does not move

In a real rebuild after the live edit (`--profile --report`), the base column
reproduces `progress.md` run 16 exactly:

```
base                              head
  nimsem     0.330s (1)             nimsem     0.328s (1)
  dceLive    0.367s (1)             dceLive    0.062s (1)
  hexer      0.269s (1)             hexer      0.267s (1)
  arkham     0.259s (3)             arkham     0.256s (3)
  link       0.125s (1)             link       0.125s (1)
  dceEmit    0.051s (1)             dceEmit    0.052s (1)
exec total   1.071s               exec total   0.762s
```

**`bench/devloop_ab.sh self.editbody` cannot see this, and that is worth
recording.** It runs the scenario five times and reports the MEDIAN, but its
edit — `if isNewScope: discard $i` inserted into `semStmt` — adds no symbol
and no use-edge, so after round 0 the module's `.dce.nif` comes out
byte-identical (P0c's sorted serialization) and the `dceLive` node is never
woken again. `--report` per round:

```
head round 0   ... dceEmit=1 dceLive=1 hexer=1 link=1 total=7
head round 1   ... dceEmit=1            hexer=1 link=1 total=6
head round 2   ... dceEmit=1            hexer=1 link=1 total=6
head round 3   ... dceEmit=1            hexer=1 link=1 total=6
head round 4   ... dceEmit=1            hexer=1 link=1 total=6
```

Four of the five rounds skip the only stage this phase changes, so the median
is the STEADY STATE. Per-round wall, two interleaved pairs:

| | round 0 (dceLive runs) | rounds 1-3 (skipped) |
|---|---|---|
| base | 1.38, 1.40 | 1.02-1.05 |
| head | 1.09, 1.10 | 1.03-1.04 |

So the first rebuild after an edit goes **1.39 -> 1.10 s** (-0.29 s, 1.26x)
and the steady state is unchanged at 1.04 s — which is exactly the 0.305 s of
`dceLive`, landing where it should. The A/B's own median moved 1.084 -> 1.069,
i.e. not at all, and reading that as "H1 bought nothing" would be wrong.

`b3d.md` §7 already noted that `dceLive` "runs on the FIRST rebuild after any
edit that changes a module's `.dce.nif`; rounds 2 and 3 of the same edit do
not run it at all". The consequence for the benchmark — that the reported
median therefore excludes it, so run 16's "the live edit's 1.08 s goes:
... dceLive 0.36 ..." mixes a first-edit stage into a steady-state wall — was
not drawn. Anyone measuring a `dceLive` change from `devloop_ab.sh`'s median
alone will measure zero.

Cold is unaffected in the other direction: a cold build runs `dceLive` once
and collects the same 0.30 s, so it goes 5.08 -> 4.79 s (-5.7 %).

## 3. What the edit shapes actually do to a `.dce.nif`

Recorded because it is what an incremental version would have had to key on,
and it is worth knowing regardless.

The headline edit (`bench/devloop_ab.sh self.editbody`, a statement inserted
into `semStmt`) changes `sem`'s `.dce.nif` and no other module's. The delta is
one added `uses` edge from `semStmt` to an already-live symbol: no root moves,
no offer moves, no module's live set changes, and P0c's `OnlyIfChanged` on the
per-module files means none of the 131 `<M>.live.nif` is rewritten. `dceLive`
runs, recomputes the same answer, and writes only the anchor.

A body-only edit that adds nothing to `roots`/`uses`/`offers` (P0c's
`self.editdead`) leaves the `.dce.nif` byte-identical, so `dceLive` is not
woken at all — that is P0c section 6's finding and it still holds.

## 4. Why no incremental live set was built

The phase was scoped on the premise that the 0.36 s was "reading 127
`.dce.nif` analyses and recomputing reachability + generic resolution for the
whole program". It was not: reading is 19 ms and reachability is 7 ms. After
the fix the stage is 51 ms against a 80 ms gate, and it splits as 19 read +
7 graph-build + 1 resolve + 7 fixpoint + 17 write.

An incremental version would persist the graph beside the anchor, digest each
module's `.dce.nif` against the previous run's, and skip the recomputation
when the delta is an understood shape. Against the measured breakdown it could
remove at most the 7 ms fixpoint and part of the 7 ms graph build — it cannot
remove the 19 ms of reads (it still has to digest every `.dce.nif` to know
which changed) nor the 17 ms of writes (the anchor is always written and the
per-module files are already `OnlyIfChanged`). So the ceiling is roughly
51 ms -> 40 ms, for:

* a new persisted state file and its format;
* a digest-vs-previous comparison per module;
* a delta classifier with an understood-shapes list and a full-recompute
  fallback, plus a `NIMONY_INCLIVE=off` switch;
* and the obligation that the incremental answer be byte-identical to the
  oracle for every edit shape — including the ones that SHRINK the live set,
  which need the previous run's per-module analysis to detect an edge removal,
  because the live set is a least fixpoint and dropping an edge can only be
  seen by comparing against the old graph.

That last point is the expensive half and it is a genuine correctness surface:
checking that the previous answer is still *closed* under the new graph is
cheap and needs only the new analysis, but checking that it is still *minimal*
is a reachability computation — i.e. `markLive` again, the 7 ms we were trying
to avoid. 11 ms is not worth that. Recorded here so the next reader does not
re-derive it.

If `dceLive` ever becomes the blocker again, the order to attack is: the 19 ms
of reads (one aggregated state file instead of 131 opens, or `mmap` + a
symbol-index that skips pool interning), then the 17 ms of writes (render each
per-module file only when its live set moved, which needs the previous set —
the same state file). The fixpoint is not the problem and has not been since
this commit.

## 5. Tests

No new test. The change is output-identical by construction and verified so in
section 2, so there is no new behaviour to pin; the scenario the phase brief
asked for (byte-identity of the per-module live files against
`NIMONY_INCLIVE=off`) has no second mode to compare against, because no second
mode was built. P0c's `incremental-live` and B3b's `decl-stability` cover the
`dceEmit` fan-out and the declaration stability that sit either side of this
stage, and both stay green.

The regression this commit is exposed to is a performance one — someone
rewriting the two chained lookups back into a `let` — and it is guarded by the
comment on `markLive` rather than by a timing assertion, which would be flaky
on a loaded machine and would not fire on the small fixtures anyway.

## 6. Residual

`resolveSymbolConflicts` iterates `for m in modules.values`, which is 131
by-value copies of a `ModuleAnalysis`, and `computeLiveSet` builds its
`graphs` table by assigning `inputs.analyses[i]`, which is 131 more. Together
they are the 8 ms of "build the table" + "resolve" above. They are left alone:
the copies are per MODULE, not per worklist pop, so they are bounded by the
program's module count rather than by its call-graph size, and removing them
would mean either an `mvalues` iteration that reads through a mutable
reference for no semantic reason or making `computeLiveSet` consume its
`DceInputs`, which `writeModuleLiveFiles` still needs afterwards.
