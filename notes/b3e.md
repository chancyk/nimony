# Phase B3e — arkham re-lowers only the changed procs of a module

Research and implementation notes per `JIT_IMPL.md`'s "Execution rules for
agents" rule 3. nimony branch `jit/b3e` (a clone at `/tmp/b3e/nimony_clone`,
forked from `55c0521e`); nativenif a private clone at `/tmp/b3e/nativenif`,
branch `jit/b3e-native`, forked from the pin `7b838ec`, five commits.

The phase is one sentence: **B3d made arkham's output a function of the
declaration it belongs to; B3e stops arkham producing the declarations that did
not change.**

---

## 1. The measurement this starts from

`notes/b3d.md` §6 probed arkham on `semygjvq21.c.nif` (the compiler's largest
module: 4.4 MB of Leng, 526 procs, 10.7 MB of asm-NIF) and reported
`collect 1 ms, procs 139 ms, total 196 ms`. This phase re-took it with the
remaining stages separated, `-d:arkhamStageProbe`, median of three, release
build (the probe was built, measured and reverted — it is not in either commit):

| stage | before | cold, cache on | warm | live edit |
|---|---|---|---|---|
| parse the 4.4 MB `.c.nif` | 14.3 | 14.2 | 14.4 | 19.0 |
| `collect` (the program model) | 1.1 | 1.1 | 1.1 | 1.1 |
| module level (types, globals, tvars) | 0.5 | 17.6 | 21.6 | 22.0 |
| **per-proc emission (526)** | **141.4** | **129.3** | **3.3** | **4.3** |
| rodata tail | 0.3 | 0.2 | 0.0 | 0.0 |
| serialize + index | 35.0 | 34.1 | 8.4 | 9.2 |
| write the file | 1.2 | 1.1 | 1.0 | 1.0 |
| **process wall** | **0.20 s** | **0.20 s** | **0.05 s** | **0.063 s** |

"module level" now carries the phase's own cost: the context digest, and on a
warm run reading the previous 10.7 MB `.asm.nif` back and hashing it. "serialize"
on a warm run is the splice (a `memcpy` per declaration), the rebuilt index and
the sidecar write.

So b3d's estimate of "196 → ~90–110 ms, the floor set by the parse and the
serialize" was pessimistic in one specific way: it assumed the splice had to
read the previous module back **into tokens** (~30 ms) and serialize the whole
thing again (~35 ms). Splicing TEXT does neither, and 63 ms is what is left.

## 2. What is cached, and why no generated byte is stored

`--asmcache:DIR` writes one `<mod>.arkham.nif` sidecar per module. It holds the
KEY of every proc arkham lowered and the byte RANGE that proc's text occupies in
the `.asm.nif` beside it — and nothing else. The bytes come from the module's
own previous output file, whose length and content hash the sidecar records.

That is `nifasm/core/asmdecls.nim`'s argument (`notes/b3d.md` §3.2) applied one
tool earlier. A cache that carried its own copy of the text would be a second
source of truth for the same bytes, and two sources that disagree — a stale
sidecar beside a rewritten module, a module produced by a different arkham —
produce a wrong `.asm.nif` silently. Here they cannot disagree: if the hash of
the file on disk is not the one recorded, the whole cache is dropped.

It also means **the file arkham is about to overwrite is the file it reads**,
which is why the flag takes a directory for the sidecar and nothing else.

### Why the text splices at all

`nifbuilder.addTree` writes `"\n"`, `nesting` spaces and `"("`. That is a
function of the DEPTH alone; `addSep` never fires after a `(` or a `)`, and
`endTree`'s `undoWhitespace` only ever eats the node's own trailing layout. A
top-level declaration is always at depth 1, so its bytes are the same wherever
in the module it sits, and the previous file's `(.index …)` offsets delimit them
exactly (they point at the leading `"\n"`, which is what makes each slice
self-contained).

The one thing that would break it is line info, which is emitted RELATIVE to the
enclosing node and would therefore change with position. asm-NIF has none —
`notes/b3d.md` §3.1 verified that over the whole corpus — and
`asmwrite.writeModule` states it as a checked precondition rather than as a
comment.

### The marker

A spliced proc is `(arkhamsplice <n>)` in the token buffer: an ordinary node the
emitters never produce, which the serializer replaces. The obvious alternative —
remembering "this proc would have been the k-th top-level child" — does not
survive `AsmBuf.finish`, whose peephole pass rebuilds the buffer and moves every
token index. A node moves with the thing it marks.

## 3. The key

### 3.1 Per proc

The line-info-blind digest of the proc's own `.c.nif` declaration
(`core/cnifdigest.nim`): hashed over the TOKEN STREAM, because a `Cursor` walks
a subtree without ever asking for its line info, so a walk that never reads it
cannot see it. Hashing the serialized bytes instead would answer "did this
MOVE", which is the question this whole mechanism exists not to ask.

That is the same trick `src/hexer/decldigest.nim` plays for F1's sidecar and the
constants are deliberately the same, but the code is not shared: that module is
written against nimony's `nifprelude` layer with its process-global
`pool`/`globalTags`, and arkham is written against bare `nifcore` with pools
passed explicitly. Importing it would drag the global pools into a tool that
does not have them.

The memo table is not an optimisation. `mixStr` costs a multiply per BYTE and
`sem.nim`'s `.c.nif` is mostly long mangled symbol names; one hash per DISTINCT
interned name is 4 ms against ~40 ms, which is the difference between the cache
paying and not.

### 3.2 Per module: the context digest

Everything the module's procs are emitted AGAINST:

* the cache format, arkham's build id (`CompileDate`/`CompileTime` plus the
  `-d:` switches that change what it emits), the target and its flags, the
  board, the word size, the input path;
* every top-level `.c.nif` declaration in order — a proc contributing its
  SIGNATURE, everything else contributing whole;
* **the answers of `cleanSigProcNames` and `noReturnProcs`.** This is the part
  that took a second look. `noReturnProcs` walks every BODY in the module to
  collect its call targets, so adding a call to `panic` inside proc A changes
  how proc B's frame is emitted. Digesting the ANSWER rather than reasoning
  about the inputs is what makes that sound, and it is free: both sets were
  computed once per module anyway, lazily, inside the first `genProc2`;
* the parts of the program model that are derived from bodies rather than from
  declarations and that a proc's text can name — `externOrder`, `syscalls`,
  `needsLibSystem`, the global/tvar/type orders, `importcOnlyGvars`,
  `gvarCName`, and the proc order with each proc's entry/asm/naked/irq flags.

### 3.3 The one exclusion, and how it was found

The first working version spliced 526 of 526 procs when nothing changed and 0
of 526 after the live edit, reporting "module context changed". Bisecting the
digest by part, then by declaration, named one: `semStmt`'s own SIGNATURE.

hexer parks an effect SUMMARY in each proc's pragmas — `(smry callsUnknown
(param 0 0 reads writes escapes) …)` — computed from that proc's body. Left in,
every proc's "signature" is a function of its own body, so an edit to one body
invalidates the module context and with it all 526 procs.

It is dropped from the signature part of the key and kept in the proc's own key
(which is the whole declaration). Sound because arkham has no reader for it: the
tag does not occur anywhere in the backend, and the only pragmas its emission
consults are `attr`, `importc`/`exportc`/`dynlib`, `varargs`, `stdcall`,
`assembler`, `naked`, `interrupt` and `inline`.

Result on the live edit: **523 spliced, 3 lowered, 3 stale** — the same 3
declarations F2's `.decls.nif` reports.

### 3.4 The state a spliced proc still owes the module

`genProc2` appends to `CodeGen.rodata` — module-level string blobs emitted after
every body, whose names are minted from the RUNNING COUNT (`"msg." &
$g.rodata.len & "." & suffix`), so one proc's contribution renames every later
proc's — and can set `needsUDiv64`/`needsSDiv64` on the firmware targets. A
`ProcRecord` carries both and a spliced proc replays them, so the counter and
the flags end up exactly where a full lowering would have left them.

That list is the modelled state and `cachedrv.endProc` is the single place a new
module-level effect has to be added to. It is a closed list only as long as
nothing new is added to `CodeGen` behind arkham's back, which is what the
identity gate is for. (For the record: the compiler corpus contains ZERO `msg.`
rodata — hexer hoists every string literal into a named const — so this is
modelled for the fixtures and for correctness, not for the headline.)

## 4. A moved dependency is a question, not a miss

The first version validated a foreign module by its file SIZE and MTIME. That
is sound and it is what the build graph itself uses, and it cost 51 ms of the
stage's 114:

An edit to `sem.nim` re-runs arkham on three modules, because arkham's node
lists the imported modules' `.c.nif` as inputs (`deps.addInlineSourceInputs`).
Two of them — `semv1g3zm` (78 procs) and the main module (9) — have untouched
declarations of their own, so every one of their procs was a splice candidate
and every one missed, on a change most of them cannot see.

`Program.foreignDecl` is the funnel that fixes it. All four call sites went
through `loadModule` + `hasDecl` + `getDecl` by hand; they go through one
procedure now, which records each read with its line-info-blind digest —
including a read that found NOTHING, which is an answer the lowering acts on
(`lookupForeignDecl` returns "not found", `gvarRefName` falls through) and which
a later run must get again.

The stamp is still asked FIRST and still answers for a whole module in one
`stat` — `notes/b3d.md` §3.3's rule, one level up — so a warm rebuild reads
nothing. Only a module whose stamp MOVED has its recorded declarations re-read.

### 4.1 Two more measurements were needed

Stamp-then-declaration still dropped the whole cache when any recorded
declaration had moved, and on this edit loop that is exactly what happens:
`semv1g3zm` reads `semStmt` and `semStmt` is what the edit changes. 0 of 78.

* **Every read is attributed to the proc that made it.**
  `Program.procReads` is snapshotted by `beginProc`/`endProc` into the
  `ProcRecord`, and `trySplice` refuses a proc that named a declaration whose
  digest moved. A read made OUTSIDE any proc goes to `moduleReads` and is the
  only kind that still drops everything — those fed `collect` and the
  whole-module analyses, i.e. the context digest itself. The read table is
  append-only and never re-sorted, because a record names its reads by INDEX
  into it and re-ordering would silently re-point every index a spliced proc
  carries.

* **`noReturnProcs`'s own reads are not recorded.** That took the module from 0
  of 78 to 76 of 78, and it is the same argument §3.2 makes for putting the
  ANSWER in the key: the analysis resolves every foreign callee of every body
  in the module to ask one question, and a change to one of those declarations
  that does not change the answer changes nothing this module emits. Safe
  because `lookupForeignDecl` caches no declaration: a proc that goes on to
  CALL one resolves it again at emission, where it is recorded against that
  proc.

### 4.2 One index space, found by reading it back

A `ProcRecord` names its reads by INDEX into the sidecar's read table, and a
proc RE-LOWERED by a warm run was recorded with indices into THIS run's table —
which starts empty and fills in emission order. Two numberings for one list. The
record then pointed at whatever read happened to sit at that position next time,
so a proc could be declared unaffected by a change it named.

It was latent: the two numberings coincide on a cold run, and on this corpus the
mispointed indices landed on unchanged entries, so every identity check still
passed. It is recorded here because that is exactly the shape of the bug this
whole phase is exposed to — a cache is only as sound as the thing it uses to say
"the same".

The fix is to make there be one numbering: `beginCachedModule` seeds the run's
table with the sidecar's, so entry `i` is the same read on both sides by
construction, and `endCachedModule` rewrites it in place instead of merging two
orders. `ForeignRead.touched` says which entries were actually read this run and
so need their digest refreshed; the rest keep the one the sidecar gave them.

Reading the rest of the state machine for the same mistake found three more
places where a numbering could outlive, or land beside, the table it indexes:
`collect` has already read a few declarations by the time the cache is loaded,
so seeding by APPENDING shifted every cache index by that many (the seed lays
the cache's table down first now and puts the earlier reads back on top of it,
renumbering the module-level set through the same map); `loadSidecar` fills the
carried state as it reads and can still refuse at its last check; and
`dropCache` cleared `reads` but not `modReads` or the stale marks. The last two
now clear the whole set together, because the set is one thing.

Result, over the whole 127-module corpus with the cache populated from the
unedited corpus and then the edited `sem.nim` swapped in:

```
  4045 procs spliced, 6 lowered, 0 modules cold
  0 of 127 .asm.nif differ from a full lowering
```

and in the compiler's own build the three arkham invocations report
`8/9`, `76/78` and `523/526` spliced.

## 5. Byte identity

* **`tests/arkhamsplice_selftest.nim`**, eight states per fixture over five
  corpus/target pairs. States 1–3 are no cache / an empty cache / a warm one.
  State 4 is the input REFORMATTED (a newline after the header), which moves
  every byte offset and every `@` suffix and no token: everything must still
  splice, because a cache that answers "changed" here is keyed on position.
  State 5 restamps every sibling module (§4) and then makes every recorded
  foreign declaration claim to have changed. State 6 invalidates one proc's key
  at a time — first, last, alternating, all — so emitted and spliced
  declarations interleave at every position there is. State 7 runs once more
  against a sidecar written by that partly spliced run, which is the state a
  second edit lands in and the one a byte range recorded from the wrong file
  would show up in.

  ```
  237 / 237 arm64      239 / 239 x64       130 / 130 cortex_m
   25 / 25  riscv32     20 / 20  avr
  ```

  State 6 perturbs the KEY rather than the input deliberately: editing a
  `.c.nif` by hand reaches one proc of one fixture, while a wrong key reaches
  every proc of every fixture and asks the same question. What it cannot ask is
  whether the key NOTICES a real edit; the compiler corpus below answers that.

* **The 127-module compiler corpus**, every module lowered with and without the
  cache, cold and warm: **0 of 127 differ**. And again with the cache populated
  from the corpus BEFORE the live edit and every module re-lowered against the
  corpus after it: **0 of 127 differ**, 4045 procs spliced.

* **The compiler built by itself**, `NIMONY_ARKHAMCACHE=off` vs on, cold then a
  live edit: 0 of 127 `.asm.nif` differ and the linked executable is
  byte-identical (both linked to ONE output path — macOS ad-hoc `codesign`
  derives the signature identifier from the output file's basename, which cost
  one false alarm here as it did in `notes/b3c.md` §0).

* **`tools/refactor_gate.sh`** against the `7b838ec` baseline: 2583 artifacts
  and 774 listings, **byte-identical**, taken again after each commit. That is
  the check that the cache is inert when it is off — every path this phase adds
  is behind `--asmcache:`, and the gate never passes it.

* **`nim r tests/tester.nim`** green end to end.

* **`hastur boot --boot-backend:native`**: stages 1 == 2 == 3.

## 8. Risks and what is left

* **The digest is 128 bits over the token stream** (two lanes), and a false
  "unchanged" is a wrong `.asm.nif` rather than a slow path. The same trade F1
  made for `<mod>.decls.nif`, at the same width. The `.asm.nif` content hash and
  the dependency stamps are 64 bits and a stamp respectively, but those only
  ever gate DROPPING the cache.
* **`(smry …)` is excluded from the signature part of the key** (§3.3). Sound
  today because arkham has no reader for it. If a backend ever starts reading a
  proc's effect summary, this exclusion becomes a miscompile and the identity
  gate would not catch it — nothing in the corpus varies a summary without
  varying the body it came from.
* **arkham's build id is `CompileDate`/`CompileTime`.** Two arkham binaries
  built from different sources within the same second would share a key. Nim's
  compile times make that not a practical hazard, but it is not a proof either;
  hashing the executable was rejected because copying `bin/arkham` into a
  toolchain would then evict every cache.
* **The floor is now the parse and the module-level digest**: 14 ms to parse the
  4.4 MB `.c.nif` and 22 ms of digest + reading the previous module back, out of
  63. Both are incremental in principle (per-declaration byte offsets in the
  `.c.nif`, which it already has an index for; a resident `bif` form of the
  previous module) and neither was attempted here.
* **A signature change still lowers the whole module.** The context digest is
  one blob over all signatures, so editing a proc's parameters invalidates its
  526 neighbours. §4 built the per-reference machinery for the CROSS-module
  case; the same treatment for same-module references — record which local
  declarations each proc named, the way `foreignDecl` records the foreign ones
  — is what would fix it, and `programs.callTarget` is the funnel it would hang
  off.
* **A `ProcRecord`'s reads are indices, not names** (§4.2). That is a size
  choice — the module's procs would otherwise carry every name they read a
  second time — and it cost FOUR latent bugs in one sitting, all of them the
  same shape. The property that keeps it sound is that
  `beginCachedModule` lays the sidecar's table down before anything else can
  extend it, and it has no test of its own: no fixture in the corpus re-lowers
  a proc that named a foreign declaration, so only the compiler corpus
  exercises it at all. If this mechanism is ever extended, naming reads by
  their key instead of by their position is the change that makes the whole
  class of mistake impossible.
* **`noReturnProcs`'s reads are deliberately untracked** (§4.1). The argument
  is that its answer is in the key and it reads nothing else; if it ever grew a
  second consumer, the exclusion would become a miscompile and the identity
  gate would not catch it — the corpus has no fixture where a foreign
  declaration changes without its module changing.
* **`dceLive` (0.366 s) is now the largest stage of a first rebuild after
  `nimsem`** — H1's, not this phase's.
