# B4 stage 1 — the design question, and the out-of-process guest

Branch `jit/b4`, worktree `/tmp/b4/nimony` beside `/tmp/b4/nativenif`
(`jit/b4-native`, still at the pin `9d7fcf78`; nothing in this stage needed a
nativenif change). `scratchpad/b4-b5-ordering.md` is the memo this stage was
launched from; where it and this file disagree, the disagreement is argued
below and the memo's inference is named.

Stage 1 had two items and a hard stop. Both are done, neither produced a
stop-and-report, and the answer to 1a makes B4's one arm64-specific component
*smaller* than the memo estimated rather than larger.

---

## 1a. Whose stack does the reload walk?

> `JIT.md` 7.4: *"Live frames are checked with nifasm's 16-byte-per-proc trace
> table (fixed-frame CFA, no CFI interpreter): a swap is deferred while a frame
> of the replaced proc is live"* — and it does not say who walks.

**Answer: the same mechanism as `lib/std/stacktraces.nim`.** The decision is
the host's; the walk is a *synchronous* walk of the guest's own stack, seeded
by a call the guest itself made. It cannot be anything else, and the reason is
in the table's own definition rather than in anybody's preference.

### The three steps that force it

**1. The walker is not in the compiler's process.** JIT.md 7.3 makes the guest
for whole programs out-of-process (`nimrun` loader over a pipe), and item 1b
below builds it. The slots a reload swaps live in the *guest's* arena
(`hostfixup.emitA64Stub`'s GOT slots on arm64, `image/memory.nim:185-194`'s
`call [rip+d32]` on x64), so the swap and the liveness question are both on the
far side of a process boundary. Reaching across it on macOS needs
`task_for_pid`, i.e. root or `com.apple.security.cs.debugger` — and the whole
runtime was built on the opposite promise: B0 measured plain RW→RX `mprotect`
working *"for a plain `nim c` binary with no entitlement and no code signature
beyond the linker's ad-hoc one"* (`nativenif/src/nifasm/hostrun.nim:28-34`).
A host-side walk would put an entitlement back into a design that deliberately
does not have one.

**2. An asynchronous walk cannot use this table.** `cfaOff` is one number per
proc and it is the state the *last* prologue step left
(`nativenif/src/nifasm/image/dwarf.nim:243-249`, `bodyCfaOff`). The table's own
header says what that costs:

> `nativenif/src/nifasm/image/tracetable.nim:36-39` — *"`cfaOff` is the DWARF
> CFA offset in the proc's BODY … It is only valid past the prologue — which is
> exactly where every frame but the innermost is, and the innermost frame's
> seed comes from a `{.naked.}` proc that has no prologue at all."*

Suspending a thread at an arbitrary instruction puts the innermost frame
*inside* a prologue with some unknowable part of SP already lowered, and no
CFI to say how much. That is precisely the state machine JIT.md 7.4 says this
table exists to avoid (*"no CFI interpreter"*). So the seed has to be a point
the guest reached by calling something — which is what `{.naked.}` gives
`stacktraces.nim`, and what a safepoint gives a reload.

**3. Therefore the walk is the guest's own, and the host asks for it.** The
compiler classifies the edit and decides to swap; the *question* "is a frame of
this proc live" is answered where the frames are, at a point the guest chose.
`stacktraces.nim`'s binary search, its `CFA - 8` return-address rule and its
`slot += cfaOff(the proc the pc belongs to)` step are the walk, unchanged. What
B4 adds is the predicate ("does any frame's pc lie in `[lo, hi)` of a replaced
proc") in place of the string, and a deferral when it does.

### Consequence for arm64 — and a correction to the memo

The memo inferred *"two arkham RISC lowerings (`mov x_d, sp`; an ADRP+ADD at
`arkham.traceinfo.0`), one `targets` set widened, one `const` widened, and a
test."* Two of those are right, one is understated, and there is a fifth item.

Confirmed, on the pin `9d7fcf78`:

* `StackPointerOp` and `TraceTableOp` have no RISC arm: `grep -rn
  "StackPointerOp\|TraceTableOp" src/arkham/risc/` is empty, and
  `risc/value.nim:3733` ends the intrinsic dispatch with `raiseAssert "arkham
  a64n: no lowering for intrinsic"`. The x64 arms are `x64/mem.nim:636` (`mov
  dst, rsp`) and `:643` (`lea dst, (lab arkham.traceinfo.0)`).
* The `TraceTable` lowering is a one-liner on the RISC side: `emAdr`
  (`risc/emit.nim:301-302`, `g.ab.tree AdrA64: g.emReg d; g.ab.sym sym`) is
  already the ADRP+ADD the memo describes, and `genTlvAddr` at `:361-375` is
  the same tree spelled for a different symbol.
* **No nifasm change is needed to make the table appear**: `traceUsed` is set
  from the arm64 operand path too (`arm64/operands.nim:315`, the twin of
  `x64/operands.nim:368`), so an `(adr d (lab arkham.traceinfo.0))` in guest
  code is enough to make `appendTraceTable` run
  (`image/writecommon.nim:33`). The memory path fills it like the file writers
  do (`image/memory.nim:102-104`).
* `src/lib/intrinsics.nim:793` already declares `StackPointer` for
  `{tgX64, tgA64}`; only `TraceTable` at `:802` is `{tgX64}`. And
  `lib/std/stacktraces.nim:27` is `defined(nimNoLibc) and defined(amd64)`.
* `{.naked.}` is supported on the RISC backend (`risc/asmproc.nim:932-976`,
  `risc/driver.nim:41-43`).

**The fifth item, which the memo did not have: the arm64 seed is a different
value, because `bl` does not push.** Work the two step rules out from
`bodyCfaOff` and they agree, which is the good news:

| | x86-64 | AArch64 |
|---|---|---|
| `bodyCfaOff` entry state | 8 (`dwarf.nim:246`) | 0 (same line) |
| callee's ra slot | `CFA - 8` (the `call` pushed it) | `CFA - 8` (the first push stores lr there — `risc/frame.nim:290-296`) |
| step from frame *P*'s ra slot to its caller *Q*'s | `cfaOff(Q)` | `cfaOff(Q)` |

So the loop body is identical, and `frame.nim:302-303`'s *"Darwin is left on the
old shape outright: its ABI requires x29 to address a valid frame record"*
means the head pair is always fp/lr on this machine. What differs is only the
**seed**. On x86-64 a `{.naked.}` proc's entry SP points *at* the caller's
pushed return address, which is why `callerFrame()` can be four lines. On
AArch64 `bl` leaves the return address in `lr` and does not move SP, so at a
naked proc's entry there is no slot holding a pc at all: the seed is the pair
(`sp - 8`, `lr`), and `lr` is not reachable through either existing intrinsic.

**So the arm64 walk is: two RISC intrinsic lowerings, ONE NEW INTRINSIC (read
`lr` in a naked proc — call it `ReturnAddress`), `TraceTable`'s `targets`
widened to `{tgX64, tgA64}`, `stackTracesAvailable` widened, a small
restructure of `getStackTrace` so the innermost pc comes from a value on one
target and from a slot on the other, and a test.** Still days rather than a
phase, and still not a design problem — but it is five items and a rewritten
seed, not "two lowerings and two widened sets".

### And a shortcut that removes all of it from B4's critical path

The paragraph above sizes *the stdlib feature* — `getStackTrace()` on arm64,
which is worth having. B4's reload check does not have to be that code.

The loader shares the guest's address space. A safepoint the guest reaches by
calling an intercepted external (`hostsyms` already resolves every external
through the host, `nativenif/src/nifasm/core/hostsyms.nim:123-145`) puts
*loader* code — ordinary Nim compiled by `nim c` — on the guest thread, in a
frame the guest called into. That is a synchronous seed by construction, and
from there the reader is a port of `stacktraces.nim` over memory the loader can
address directly. It needs **nothing from arkham**: no intrinsic, no widened
target set, no guest-side walker.

It needs two small things nifasm does not have today, both platform-neutral:

1. a way to say *"emit the trace table"* without guest code referencing
   `arkham.traceinfo.0` — today `ctx.traceUsed` is only ever set by an operand
   naming the symbol (`arm64/operands.nim:315`, `x64/operands.nim:368,1713`);
2. the table's runtime address on `MemImage`, which carries `codeVaddr`,
   `dataVaddr`, `entry`, `procs` and `externals` and no table
   (`image/memory.nim:69-79`). `ctx.traceLabel`'s position is known at
   `fillTraceTable` time, so this is a field, not a computation.

The seed itself is the one place the two targets differ again, and the same
`bl`-does-not-push asymmetry decides it: on Darwin/arm64 the clean seed is the
frame-record chain (`__builtin_frame_address(0)` in the intercept, then
`[fp] / [fp+8]`), which arkham guarantees here (`frame.nim:302-303`) and does
*not* guarantee on linux/arm64, where the same file drops x29 when it can. On
x86-64 the table's own step rule is the portable one.

**Recommendation for stage 2, not settled here:** build the loader-side variant
for B4 (it is the smaller half of a phase and needs no arkham work), and keep
the arm64 `getStackTrace` as its own item — it is a stdlib feature that B3e's
and F1's work has nothing to do with, and B4 does not block on it.

### What this does *not* change

B4 is the phase `JIT_IMPL.md` describes. The walk is the mechanism JIT.md 7.4
names, on the table nifasm already emits, with the step rule
`lib/std/stacktraces.nim` already implements. No stop-and-report.

## 1b. The `nimrun` out-of-process guest

### What was actually blocking

`notes/b1-nimony.md:372` says a `nimony dev` running many programs in one
process *"would have to, and cannot"* release the arena. That is right about
the leak and slightly wrong about the word "cannot": **a second in-process run
works.** `runImage` clears `gGuest.running` after a guest finishes
(`nativenif/src/nifasm/hostrun.nim:266`), so nothing refuses the second call.
Measured, on this machine, with the two paths in one binary
(`RunProgram` × N, hello-world, warm blob cache):

| N runs from ONE host process | threads after | mapped address space | wall |
|---|---|---|---|
| 1 in-process | 2 | +272 MB | 0.02 s |
| 5 in-process | 6 | +1.36 GB | 0.06 s |
| 20 in-process | 21 | +5.42 GB | 0.21 s |
| 50 in-process | 51 | +13.56 GB | 0.52 s |
| 1 / 5 / 20 / 50 through `nimrun` | **1** | **0** | 0.01 / 0.02 / 0.06 / 0.15 s |

271 MB per run is the 256 MB arena plus the guest thread's 8 MB stack, and the
thread is `guestExit` parked forever. So the honest statement is: the
in-process path degrades linearly and unboundedly, at 10.2 ms and a quarter of
a gigabyte of address space per run, against 2.9 ms and nothing. It is not that
the second program fails; it is that the hundredth does, and that a `nimony
dev` session has no way to stop a program it is about to replace.

That third thing is the one no measurement shows and it is the reason the
boundary is not optional: there is no way to kill a guest thread from outside
(`hostrun.nim`'s header: the three ways out of a foreign frame are `longjmp`,
unwinding and not leaving), so an in-process `dev` could never restart a
running program — which is exactly what JIT.md 7.4 calls for on a signature
edit.

### What was built

Three files, ~600 lines, all platform-neutral POSIX. Nothing in nativenif
moved.

* **`src/nimony/guestwire.nim`** — the wire. One `AF_UNIX` `socketpair`
  `dup2`'d onto descriptor 3 in the child (`GuestControlFd`), records framed as
  a decimal field count and then a decimal length and that many bytes, three
  record shapes (`hello` / `run` / `ran`|`refused`), plus `spawnGuest`,
  `closeChannel`, `reapGuest` and `reraiseAsGuestDid`. State lives in
  `GuestChannel` and `GuestLaunch`; there are no new global `var`s.
* **`src/nimony/nimrun.nim`** — the loader. It parses `--control-fd:`, sends
  the handshake, reads one `run` record, and calls
  **`engine.runWholeProgram`** — the very proc `nimony r` calls in its own
  process — then sends the result back and `_exit`s. That is the design's main
  claim: running a program out of process is *not a second implementation* of
  running a program. The assembler, the arena, the symbol resolution, the
  `ThreadSpawners` refusal, the blob cache and the `--verbose` line are one
  body of code with a `posix_spawn` in front of it, so "byte-identical to
  `nimony r`" is a property of the arrangement instead of two copies to keep in
  step.
* **`engine.runWholeProgramOutOfProcess`** — the compiler's half, at the bottom
  of `engine.nim` where its header already promised it (*"Everything below
  `runWholeProgram` is deliberately inside that one proc, so that B3's
  out-of-process `nimrun` guest can replace it whole"*). `RunProgram` in,
  `RunResult` out, never raises.

Wired up as `nimony r --guest:inproc|subprocess`, **default `inproc`** — every
number in `bench/` was taken on the in-process path and a `nimony r` process
still runs one program and exits, so the leak lives for milliseconds there.
`hastur build all` and `hastur build nimony` build `nimrun` beside `nimony`,
guarded by the same `engineFlags()` that guards the engine itself.

### Four decisions worth naming

**Descriptors 0, 1 and 2 are inherited untouched.** The loader does not pipe
the guest's output back; the guest writes to the user's terminal directly.
That removes a copy, an interleaving policy and a class of deadlock, and it is
*why* the two paths are byte-identical rather than merely tested to be.

**`posix_spawn`, not `fork` + `execv`.** Everything between a `fork` and its
`exec` must be async-signal-safe, and this process has a collector, buffered
streams and (under `nimony c`) worker threads. The file actions say exactly one
thing: move our end of the socketpair onto descriptor 3.

**One loader process runs exactly one program.** Not a limitation worked
around — it is what makes `exit` trivial. The parked thread, its stack and the
256 MB arena are all reclaimed by the kernel when the loader ends, and there is
never a second guest for `runImage` to refuse.

**A guest that dies from a signal is re-raised in the compiler, not translated
to `128 + n`.** In-process, `cAbort`'s `kill(getpid(), SIGABRT)` lands on the
compiler and the shell reports 134 from a *wait status*. Out of process the
signal lands on the loader; reporting an ordinary exit code of 134 would print
the same number and be a different thing, which `wait`, `set -e` and any
harness reading the status can tell apart. So `reraiseAsGuestDid` puts the
handler back to `SIG_DFL` and raises the same signal here. Verified by hand:
an `abort()`ing program gives `SIGABRT: Abnormal termination.` and 134 on both
paths.

### The gate, and its output

> a guest program runs to completion, exits, and a **second** program runs in
> the same host process, with output byte-identical to two separate `nimony r`
> invocations.

`tests/inproc/guest/` — `setup.nim` builds and runs two *different* programs
with `bin/nimony r` (that is the reference and it is also what produces the
`.asm.nif` modules), then compiles `driver.nim` against `src/nimony/engine` and
runs it **once**; the driver runs both programs through
`runWholeProgramOutOfProcess`, each with its stdout `dup2`'d onto a file, and
reports its own thread count before and after.

```
[inproc/guest] ok: one: `nimony r` -> status 0, 37 bytes of stdout (module one1ij88h1)
[inproc/guest] ok: two: `nimony r` -> status 7, 23 bytes of stdout (module two7gih181)
[inproc/guest] ok: one host process ran both programs and is still running
[inproc/guest] ok: program one: exit status 0 both ways
[inproc/guest] ok: program one: stdout byte-identical to `nimony r` (37 bytes)
[inproc/guest] ok: program two: exit status 7 both ways
[inproc/guest] ok: program two: stdout byte-identical to `nimony r` (23 bytes)
[inproc/guest] ok: the host still has 1 thread(s) after both runs (in-process, each `exit` parks one forever)
[inproc/guest] all checks passed
```

The driver goes into a `bin/` of its own with a copy of `nimrun` beside it.
That is not a test artifice: `findTool` resolves next to the running executable
and nowhere else (no cwd, no `PATH` — the `small items` fix), so any host that
embeds the engine ships `nimrun` in its own toolchain directory.

`tests/nimony_r` gained a differential block against the **in-process** run
(the linked executable is already covered there) over the five shapes a program
can end in:

```
  ok   out-of-process hello (both ways: 0, 1 line(s))
  ok   out-of-process quit (both ways: 3, 1 line(s))
  ok   out-of-process panic (both ways: 1, 5 line(s))
  ok   out-of-process argv (both ways: 0, 3 line(s))
  ok   out-of-process streams (both ways: 0, 4 line(s))
```

And by hand, the largest program in the repository: `nimony r
--guest:subprocess src/nimony/nimony.nim --version` prints `0.6.0` in 5.2 s
cold. `--verbose`'s `[run-engine]` line is byte-identical between the two
paths, because the loader prints it — it is the same `runTimingLine` call.

### Not done, and deliberately

* **The loader does not stay alive across programs.** It reads one `run` record
  and ends. Hot reload needs it to keep the channel open while the program runs
  and to take `swap`/`restart` records on it; the framing already carries an
  arbitrary verb, and `GuestLaunch` is already the object that would hold the
  live one.
* **No `nimony dev`.** Stage 2.
* **`--guest:subprocess` is opt-in.** Flipping the default is a benchmark
  decision, not this stage's: it would change `self.run`/`self.nrun` in
  `bench/devloop_bench.sh`, and on the numbers above it would *improve* them.
* **The CTFE engine still runs in-process** and should: `evaluate` captures the
  guest's output into the compiler's diagnostics and has a budget, and a
  `const` fold does not want a process. `--ctfe:subprocess` remains the
  fallback shape there.
