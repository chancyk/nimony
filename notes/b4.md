## 1a. Whose stack does the reload walk?

> `JIT.md` 7.4: *"Live frames are checked with nifasm's 16-byte-per-proc trace
> table (fixed-frame CFA, no CFI interpreter): a swap is deferred while a frame
> of the replaced proc is live"* — and it does not say who walks.

**Answer: the same mechanism as `lib/std/stacktraces.nim`.** The decision is
the host's; the walk is a *synchronous* walk of the guest's own stack, seeded
by a call the guest itself made. It cannot be anything else, and the reason is
in the table's own definition rather than in anybody's preference.

### The three steps that force it

**1. The walker is not in the compiler's process.** JIT.md 7.3 makes the guest
for whole programs out-of-process (`nimrun` loader over a pipe), and item 1b
below builds it. The slots a reload swaps live in the *guest's* arena
(`hostfixup.emitA64Stub`'s GOT slots on arm64, `image/memory.nim:185-194`'s
`call [rip+d32]` on x64), so the swap and the liveness question are both on the
far side of a process boundary. Reaching across it on macOS needs
`task_for_pid`, i.e. root or `com.apple.security.cs.debugger` — and the whole
runtime was built on the opposite promise: B0 measured plain RW→RX `mprotect`
working *"for a plain `nim c` binary with no entitlement and no code signature
beyond the linker's ad-hoc one"* (`nativenif/src/nifasm/hostrun.nim:28-34`).
A host-side walk would put an entitlement back into a design that deliberately
does not have one.

**2. An asynchronous walk cannot use this table.** `cfaOff` is one number per
proc and it is the state the *last* prologue step left
(`nativenif/src/nifasm/image/dwarf.nim:243-249`, `bodyCfaOff`). The table's own
header says what that costs:

> `nativenif/src/nifasm/image/tracetable.nim:36-39` — *"`cfaOff` is the DWARF
> CFA offset in the proc's BODY … It is only valid past the prologue — which is
> exactly where every frame but the innermost is, and the innermost frame's
> seed comes from a `{.naked.}` proc that has no prologue at all."*

Suspending a thread at an arbitrary instruction puts the innermost frame
*inside* a prologue with some unknowable part of SP already lowered, and no
CFI to say how much. That is precisely the state machine JIT.md 7.4 says this
table exists to avoid (*"no CFI interpreter"*). So the seed has to be a point
the guest reached by calling something — which is what `{.naked.}` gives
`stacktraces.nim`, and what a safepoint gives a reload.

**3. Therefore the walk is the guest's own, and the host asks for it.** The
compiler classifies the edit and decides to swap; the *question* "is a frame of
this proc live" is answered where the frames are, at a point the guest chose.
`stacktraces.nim`'s binary search, its `CFA - 8` return-address rule and its
`slot += cfaOff(the proc the pc belongs to)` step are the walk, unchanged. What
B4 adds is the predicate ("does any frame's pc lie in `[lo, hi)` of a replaced
proc") in place of the string, and a deferral when it does.

### Consequence for arm64 — and a correction to the memo

The memo inferred *"two arkham RISC lowerings (`mov x_d, sp`; an ADRP+ADD at
`arkham.traceinfo.0`), one `targets` set widened, one `const` widened, and a
test."* Two of those are right, one is understated, and there is a fifth item.

Confirmed, on the pin `9d7fcf78`:

* `StackPointerOp` and `TraceTableOp` have no RISC arm: `grep -rn
  "StackPointerOp\|TraceTableOp" src/arkham/risc/` is empty, and
  `risc/value.nim:3733` ends the intrinsic dispatch with `raiseAssert "arkham
  a64n: no lowering for intrinsic"`. The x64 arms are `x64/mem.nim:636` (`mov
  dst, rsp`) and `:643` (`lea dst, (lab arkham.traceinfo.0)`).
* The `TraceTable` lowering is a one-liner on the RISC side: `emAdr`
  (`risc/emit.nim:301-302`, `g.ab.tree AdrA64: g.emReg d; g.ab.sym sym`) is
  already the ADRP+ADD the memo describes, and `genTlvAddr` at `:361-375` is
  the same tree spelled for a different symbol.
* **No nifasm change is needed to make the table appear**: `traceUsed` is set
  from the arm64 operand path too (`arm64/operands.nim:315`, the twin of
  `x64/operands.nim:368`), so an `(adr d (lab arkham.traceinfo.0))` in guest
  code is enough to make `appendTraceTable` run
  (`image/writecommon.nim:33`). The memory path fills it like the file writers
  do (`image/memory.nim:102-104`).
* `src/lib/intrinsics.nim:793` already declares `StackPointer` for
  `{tgX64, tgA64}`; only `TraceTable` at `:802` is `{tgX64}`. And
  `lib/std/stacktraces.nim:27` is `defined(nimNoLibc) and defined(amd64)`.
* `{.naked.}` is supported on the RISC backend (`risc/asmproc.nim:932-976`,
  `risc/driver.nim:41-43`).

**The fifth item, which the memo did not have: the arm64 seed is a different
value, because `bl` does not push.** Work the two step rules out from
`bodyCfaOff` and they agree, which is the good news:

| | x86-64 | AArch64 |
|---|---|---|
| `bodyCfaOff` entry state | 8 (`dwarf.nim:246`) | 0 (same line) |
| callee's ra slot | `CFA - 8` (the `call` pushed it) | `CFA - 8` (the first push stores lr there — `risc/frame.nim:290-296`) |
| step from frame *P*'s ra slot to its caller *Q*'s | `cfaOff(Q)` | `cfaOff(Q)` |

So the loop body is identical, and `frame.nim:302-303`'s *"Darwin is left on the
old shape outright: its ABI requires x29 to address a valid frame record"*
means the head pair is always fp/lr on this machine. What differs is only the
**seed**. On x86-64 a `{.naked.}` proc's entry SP points *at* the caller's
pushed return address, which is why `callerFrame()` can be four lines. On
AArch64 `bl` leaves the return address in `lr` and does not move SP, so at a
naked proc's entry there is no slot holding a pc at all: the seed is the pair
(`sp - 8`, `lr`), and `lr` is not reachable through either existing intrinsic.

**So the arm64 walk is: two RISC intrinsic lowerings, ONE NEW INTRINSIC (read
`lr` in a naked proc — call it `ReturnAddress`), `TraceTable`'s `targets`
widened to `{tgX64, tgA64}`, `stackTracesAvailable` widened, a small
restructure of `getStackTrace` so the innermost pc comes from a value on one
target and from a slot on the other, and a test.** Still days rather than a
phase, and still not a design problem — but it is five items and a rewritten
seed, not "two lowerings and two widened sets".

### And a shortcut that removes all of it from B4's critical path

The paragraph above sizes *the stdlib feature* — `getStackTrace()` on arm64,
which is worth having. B4's reload check does not have to be that code.

The loader shares the guest's address space. A safepoint the guest reaches by
calling an intercepted external (`hostsyms` already resolves every external
through the host, `nativenif/src/nifasm/core/hostsyms.nim:123-145`) puts
*loader* code — ordinary Nim compiled by `nim c` — on the guest thread, in a
frame the guest called into. That is a synchronous seed by construction, and
from there the reader is a port of `stacktraces.nim` over memory the loader can
address directly. It needs **nothing from arkham**: no intrinsic, no widened
target set, no guest-side walker.

It needs two small things nifasm does not have today, both platform-neutral:

1. a way to say *"emit the trace table"* without guest code referencing
   `arkham.traceinfo.0` — today `ctx.traceUsed` is only ever set by an operand
   naming the symbol (`arm64/operands.nim:315`, `x64/operands.nim:368,1713`);
2. the table's runtime address on `MemImage`, which carries `codeVaddr`,
   `dataVaddr`, `entry`, `procs` and `externals` and no table
   (`image/memory.nim:69-79`). `ctx.traceLabel`'s position is known at
   `fillTraceTable` time, so this is a field, not a computation.

The seed itself is the one place the two targets differ again, and the same
`bl`-does-not-push asymmetry decides it: on Darwin/arm64 the clean seed is the
frame-record chain (`__builtin_frame_address(0)` in the intercept, then
`[fp] / [fp+8]`), which arkham guarantees here (`frame.nim:302-303`) and does
*not* guarantee on linux/arm64, where the same file drops x29 when it can. On
x86-64 the table's own step rule is the portable one.

**Recommendation for stage 2, not settled here:** build the loader-side variant
for B4 (it is the smaller half of a phase and needs no arkham work), and keep
the arm64 `getStackTrace` as its own item — it is a stdlib feature that B3e's
and F1's work has nothing to do with, and B4 does not block on it.

### What this does *not* change

B4 is the phase `JIT_IMPL.md` describes. The walk is the mechanism JIT.md 7.4
names, on the table nifasm already emits, with the step rule
`lib/std/stacktraces.nim` already implements. No stop-and-report.

## 1b. The `nimrun` out-of-process guest

### What was actually blocking

`notes/b1-nimony.md:372` says a `nimony dev` running many programs in one
process *"would have to, and cannot"* release the arena. That is right about
the leak and slightly wrong about the word "cannot": **a second in-process run
works.** `runImage` clears `gGuest.running` after a guest finishes
(`nativenif/src/nifasm/hostrun.nim:266`), so nothing refuses the second call.
Measured, on this machine, with the two paths in one binary
(`RunProgram` × N, hello-world, warm blob cache):

| N runs from ONE host process | threads after | mapped address space | wall |
|---|---|---|---|
| 1 in-process | 2 | +272 MB | 0.02 s |
| 5 in-process | 6 | +1.36 GB | 0.06 s |
| 20 in-process | 21 | +5.42 GB | 0.21 s |
| 50 in-process | 51 | +13.56 GB | 0.52 s |
| 1 / 5 / 20 / 50 through `nimrun` | **1** | **0** | 0.01 / 0.02 / 0.06 / 0.15 s |

271 MB per run is the 256 MB arena plus the guest thread's 8 MB stack, and the
thread is `guestExit` parked forever. So the honest statement is: the
in-process path degrades linearly and unboundedly, at 10.2 ms and a quarter of
a gigabyte of address space per run, against 2.9 ms and nothing. It is not that
the second program fails; it is that the hundredth does, and that a `nimony
dev` session has no way to stop a program it is about to replace.

That third thing is the one no measurement shows and it is the reason the
boundary is not optional: there is no way to kill a guest thread from outside
(`hostrun.nim`'s header: the three ways out of a foreign frame are `longjmp`,
unwinding and not leaving), so an in-process `dev` could never restart a
running program — which is exactly what JIT.md 7.4 calls for on a signature
edit.

### What was built

Three files, ~600 lines, all platform-neutral POSIX. Nothing in nativenif
moved.

* **`src/nimony/guestwire.nim`** — the wire. One `AF_UNIX` `socketpair`
  `dup2`'d onto descriptor 3 in the child (`GuestControlFd`), records framed as
  a decimal field count and then a decimal length and that many bytes, three
  record shapes (`hello` / `run` / `ran`|`refused`), plus `spawnGuest`,
  `closeChannel`, `reapGuest` and `reraiseAsGuestDid`. State lives in
  `GuestChannel` and `GuestLaunch`; there are no new global `var`s.
* **`src/nimony/nimrun.nim`** — the loader. It parses `--control-fd:`, sends
  the handshake, reads one `run` record, and calls
  **`engine.runWholeProgram`** — the very proc `nimony r` calls in its own
  process — then sends the result back and `_exit`s. That is the design's main
  claim: running a program out of process is *not a second implementation* of
  running a program. The assembler, the arena, the symbol resolution, the
  `ThreadSpawners` refusal, the blob cache and the `--verbose` line are one
  body of code with a `posix_spawn` in front of it, so "byte-identical to
  `nimony r`" is a property of the arrangement instead of two copies to keep in
  step.
* **`engine.runWholeProgramOutOfProcess`** — the compiler's half, at the bottom
  of `engine.nim` where its header already promised it (*"Everything below
  `runWholeProgram` is deliberately inside that one proc, so that B3's
  out-of-process `nimrun` guest can replace it whole"*). `RunProgram` in,
  `RunResult` out, never raises.

Wired up as `nimony r --guest:inproc|subprocess`, **default `inproc`** — every
number in `bench/` was taken on the in-process path and a `nimony r` process
still runs one program and exits, so the leak lives for milliseconds there.
`hastur build all` and `hastur build nimony` build `nimrun` beside `nimony`,
guarded by the same `engineFlags()` that guards the engine itself.

### Four decisions worth naming

**Descriptors 0, 1 and 2 are inherited untouched.** The loader does not pipe
the guest's output back; the guest writes to the user's terminal directly.
That removes a copy, an interleaving policy and a class of deadlock, and it is
*why* the two paths are byte-identical rather than merely tested to be.

**`posix_spawn`, not `fork` + `execv`.** Everything between a `fork` and its
`exec` must be async-signal-safe, and this process has a collector, buffered
streams and (under `nimony c`) worker threads. The file actions say exactly one
thing: move our end of the socketpair onto descriptor 3.

**One loader process runs exactly one program.** Not a limitation worked
around — it is what makes `exit` trivial. The parked thread, its stack and the
256 MB arena are all reclaimed by the kernel when the loader ends, and there is
never a second guest for `runImage` to refuse.

**A guest that dies from a signal is re-raised in the compiler, not translated
to `128 + n`.** In-process, `cAbort`'s `kill(getpid(), SIGABRT)` lands on the
compiler and the shell reports 134 from a *wait status*. Out of process the
signal lands on the loader; reporting an ordinary exit code of 134 would print
the same number and be a different thing, which `wait`, `set -e` and any
harness reading the status can tell apart. So `reraiseAsGuestDid` puts the
handler back to `SIG_DFL` and raises the same signal here. Verified by hand:
an `abort()`ing program gives `SIGABRT: Abnormal termination.` and 134 on both
paths.

### The gate, and its output

> a guest program runs to completion, exits, and a **second** program runs in
> the same host process, with output byte-identical to two separate `nimony r`
> invocations.

`tests/inproc/guest/` — `setup.nim` builds and runs two *different* programs
with `bin/nimony r` (that is the reference and it is also what produces the
`.asm.nif` modules), then compiles `driver.nim` against `src/nimony/engine` and
runs it **once**; the driver runs both programs through
`runWholeProgramOutOfProcess`, each with its stdout `dup2`'d onto a file, and
reports its own thread count before and after.

```
[inproc/guest] ok: one: `nimony r` -> status 0, 37 bytes of stdout (module one1ij88h1)
[inproc/guest] ok: two: `nimony r` -> status 7, 23 bytes of stdout (module two7gih181)
[inproc/guest] ok: one host process ran both programs and is still running
[inproc/guest] ok: program one: exit status 0 both ways
[inproc/guest] ok: program one: stdout byte-identical to `nimony r` (37 bytes)
[inproc/guest] ok: program two: exit status 7 both ways
[inproc/guest] ok: program two: stdout byte-identical to `nimony r` (23 bytes)
[inproc/guest] ok: the host still has 1 thread(s) after both runs (in-process, each `exit` parks one forever)

The driver goes into a `bin/` of its own with a copy of `nimrun` beside it.
That is not a test artifice: `findTool` resolves next to the running executable

embeds the engine ships `nimrun` in its own toolchain directory.

`tests/nimony_r` gained a differential block against the **in-process** run
(the linked executable is already covered there) over the five shapes a program
can end in:

```
  ok   out-of-process hello (both ways: 0, 1 line(s))
  ok   out-of-process quit (both ways: 3, 1 line(s))
  ok   out-of-process panic (both ways: 1, 5 line(s))
  ok   out-of-process argv (both ways: 0, 3 line(s))

And by hand, the largest program in the repository: `nimony r
--guest:subprocess src/nimony/nimony.nim --version` prints `0.6.0` in 5.2 s
cold. `--verbose`'s `[run-engine]` line is byte-identical between the two

### Cost on the compile path: none

Run 21 of `bench/results/2026-09-07/progress.md`, interleaved, A =
`/tmp/merge-u1` (`95fff89d`, which is the tip's code -- `5df66183` touches no
`src/`), B = this branch: `self.editbody` 1.018 / 1.044 s cpu / 107 MB against

a flag arm that no compile-graph node reaches, and the numbers say so.

The first attempt at this measurement used the main checkout as the base and
read 1.127. That is the merge chain, not the change: the main tree is at the
tip commit but its `bin/nimony` was built before it. `BENCHMARK.md` §1 now

### Reproducing the leak table

The N-runs-from-one-host-process numbers came from a throwaway program that
calls `runWholeProgram` or `runWholeProgramOutOfProcess` N times and reports
`ps -M | wc -l` and `ps -o vsz=` around the loop. It is ~25 lines against
`src/nimony/engine`, compiled with the same flags
`tests/inproc/guest/setup.nim` passes its driver, and it has to live in a
directory whose name starts with `bin` (or have one) so that `findTool` can
see `nimrun` beside it. Not kept: `tests/inproc/guest` asserts the property
that matters (the thread count does not move), and the table above is the
measurement behind the phase rather than a thing to re-run.

### Not done, and deliberately

* **The loader does not stay alive across programs.** It reads one `run` record
  and ends. Hot reload needs it to keep the channel open while the program runs
  and to take `swap`/`restart` records on it; the framing already carries an
  arbitrary verb, and `GuestLaunch` is already the object that would hold the
  live one.
* **No `nimony dev`.** Stage 2.
* **`--guest:subprocess` is opt-in.** Flipping the default is a benchmark
  decision, not this stage's: it would change `self.run`/`self.nrun` in
  `bench/devloop_bench.sh`, and on the numbers above it would *improve* them.
* **The CTFE engine still runs in-process** and should: `evaluate` captures the
  guest's output into the compiler's diagnostics and has a budget, and a
  `const` fold does not want a process. `--ctfe:subprocess` remains the
  fallback shape there.

# B4 stage 2 — hot reload, `nimony dev`, and the demo

Same branch and worktree. Stage 1's two items are unchanged by anything below;
this is the other six, in the order stage 1's findings put them.

## The stop-early condition fired, and here is what it was

The coordinator's instruction was to stop if *"the slot indirection needs
something the `extproc` path does not already provide"*. **It does.** Both
halves of JIT.md 7.3's build-time mechanism are absent from the two tools:

* **arkham decides `extproc` from the Leng declaration alone.**
  `arkham/core/programs.nim`'s `collect`, `ProcS` branch: an `importc` name that
  is a known syscall becomes a `syproc` (:799), any other `importc` becomes an
  extproc (:830-879), and a proc with a body becomes an ordinary in-image proc
  (:882-890). `foreignCallTarget` (:1078-1132) re-derives the identical
  classification for a foreign module, commented *"classify the foreign decl
  EXACTLY as the owning module's pass 0 did"*. `arkham.nim`'s CLI has
  `--output`, `--arch`, `--asmcache*`, `--os`, `--cpu`, `--layout` and nothing
  else; `Program`/`collect` take `darwin` and `windows` and nothing else.
  `grep -rn "forceExtern|forceExtproc|alwaysExtern"` over `src/` is empty.
* **nifasm follows a foreign symbol into its module unconditionally.**
  `core/typesem.lookupWithAutoImport:405-452` calls `openForeignModule` at :418
  whenever a name's module suffix differs from `ctx.thisModule`, against no
  exclusion set; `core/modules.openForeignModule:151-171` opens
  `<baseDir>/<mod>.asm.nif` and `error`s at :164 if the file is absent. No
  `AsmSession` or `GenContext` field says "do not follow into module X".

So "reloadable module -> slot indirection, the `extproc` branch of `pass1`, an
existing tested path" is true of the **run-time** half and not of the
**build-time** half: the slots exist and are exercised on both architectures,
and nothing can make a proc with a body reach its callers through one.

Rather than build that (an arkham option threaded through two classifications
plus a nifasm exclusion set, and a re-pin for both), stage 2 installs the same
indirection **at the first reload instead of at every call site in advance**.
The reasoning, and the experiment that settled it, are below. This is a
deviation from JIT.md 7.3's sentence and it is written down here rather than
there (execution rule 6).

## What a reload is, and the experiment that proved it

Four steps. Only the second is new machinery.

1. **The compiler assembles the whole edited program again.** After B3d/B3e
   that is the cheap part -- `self.editbody` assembles in 0.09 s -- and a whole
   image is the one thing that needs nothing new from arkham or nifasm.
2. **The loader lays that image's CODE into free space further up the same
   arena, and hands it the LIVE image's data region as its data ADDRESSES.**
   `MemRegion` separates `at` (where the bytes go now) from `vaddr` (the address
   byte 0 will have), and says in `image/memory.nim` that it is separate *"so
   that a test can lay an image out at the addresses some other container chose
   without having to map anything there"*. So the new code reads and writes the
   globals the running program already has, while its own freshly computed
   initializers are written to a scratch buffer and discarded.
3. **The guest's stack is walked at a safepoint.** A proc with a live frame is
   not replaced; the swap is deferred.
4. **Each replaced proc's ENTRY in the live image is overwritten** with the same
   12-byte `adrp x16 / ldr x16 / br x16` stub `image/hostfixup.emitA64Stub`
   writes for an external call, jumping through a slot allocated at the top of
   the data region. The first reload of a proc installs the stub; every later
   one rewrites the slot alone.

Step 2 was the assumption worth testing first, and it was tested before a line
of the phase was built. A throwaway host assembled `relaydemo.nim`, laid it,
ran it, then assembled an **edited** copy of the same module into free arena
space with the live data region's addresses and redirected one proc:

```
img1: code 25820 data 13128 ext 6 procs 115 trace yes
img2: code 25820 data 13128 ext 6 procs 115 trace yes
layout match: dataLen true externs true
redirect tick.0.relqisyix: 00000001056D4164 -> 00000001056DC164
a=100
b=200
c=300
guest outcome goExited status 0
```

The program's `main` is image 1's, its `bl` to `tick` is a direct branch, and it
printed `100/200/300` -- the edited body -- while `counter`, a global,
incremented 1, 2, 3 across the boundary. That is hot reload's whole mechanism,
working, with zero arkham changes.

Why it is safe to overwrite a running image's code here: the guest is
single-threaded by construction (`image/memory.nim:27-38` refuses an image
carrying a thread-local, and `engine.ThreadSpawners` refuses one that could make
a thread), and at the moment of the patch that one thread is parked inside the
loader's intercept. Nothing is executing the bytes being written. x16 is IP0,
the ABI's inter-procedural scratch register, dead at every call boundary -- and
a proc's first instruction is exactly one.

## The six components

### 1. The loader-side stack walk (`src/nimony/devwalk.nim`)

Stage 1 settled that the walk is synchronous and in the guest's address space.
The safepoint gives it a seed for free: the guest calls `nimony_dev_poll`, an
ordinary external, and the loader's intercept answers it **on the guest's
thread, in a frame the guest called**. From there the walk is host Nim over
shared memory -- no intrinsic, no guest-side walker, nothing from arkham.

Frames are stepped by the frame-record chain rather than by `cfaOff`, and the
two coincide: arkham keeps x29 addressing a valid `{fp, lr}` pair on Darwin
outright (`risc/frame.nim:302-303`) and keeps lr at `CFA - 8` (`:290-296`),
which for a frame whose head pair is fp/lr is `fp + 8`. The **table is still the
mechanism** and is the half that cannot be replaced: a return address is a
number, and only the table says which proc contains it -- `MemImage.procs` gives
entries, not extents.

Two nativenif additions, both sanctioned in stage 1, both three lines
(`ad886112`): `AsmSession.wantTraceTable` (nothing in a guest references
`arkham.traceinfo.0`, so the table has to be asked for) and
`MemImage.traceTable` (the caller cannot compute it -- the table is an
`skLabel`, and `procs` holds only `skProc`).

### 2. The loader stays alive (`nimrun`, `guestwire`, `engine`)

`swap` on the same framing; `swapped`/`deferred`/`failed` back.
`GuestChannel.hasPending` makes the safepoint's check non-blocking, so a
program that polls every iteration is not held up by a compiler with nothing to
say. `engine.startDevGuest`/`askSwap`/`pollDevGuest`/`stopDevGuest` are the
one-shot `runWholeProgramOutOfProcess` taken apart, because the interesting part
happens between its steps.

A **restart** is `SIGTERM` and a fresh loader, not a protocol verb. That is the
half of JIT.md 7.4's *"or restart the guest"* only a process boundary can do:
there is no way to stop a guest THREAD from outside, which is precisely why an
in-process `nimony dev` could never restart a program it had decided to replace.

`DevState` in `nimrun.nim` is a module-level `var` and has to be, for the reason
`hostrun.gGuest` and `engine.gIo` are: an intercept is reached through a C
function pointer the guest holds, so it can carry no context but a global. It is
sound for the same reason -- one guest, one process -- and it is only ever
touched on the guest's thread while the loader's main thread is parked in
`waitForGuest`.

### 3. The classifier (`src/nimony/devclassify.nim`)

Reads every `<mod>.c.nif` and reduces each top-level declaration to (tag, header
digest, body digest), using `decldigest.digestTree` so it inherits F1's line-info
blindness rather than re-deriving it.

**Why not `<mod>.decls.nif`, which the build already writes.** `DeclDigest` has
`input` and `output` and no notion of a declaration's KIND or of the line between
a proc's signature and its body -- and "a body edit" versus "a signature edit"
are exactly the two answers this phase has to give. Splitting the digest in
`hexer/decldigest.nim` is the efficient home for it and is the follow-up; doing
it in the classifier first keeps the phase off the frontend's output format,
which `decl-stability` pins.

**No layout sidecar, and it is not needed for soundness.** JIT.md 7.4 names a
per-module `(layouts …)` sidecar from nifasm's `typesem` for detecting type
layout changes. The classifier does not need one, because it is stricter: it
says *reload* only when **every** changed declaration in **every** module is a
proc whose header is unchanged. If no type declaration anywhere changed, no
layout changed -- a type's layout can only move if it or something it embeds was
edited, and both are declarations in some module's `.c.nif`. The sidecar would
buy back the cases this refuses (adding a method to a type, a field that does
not move an offset), i.e. it makes the classifier say yes MORE OFTEN; it is not
what makes it correct. Two other deliberate strictnesses: a **new global** is a
restart (JIT.md allows it against an "append-only data arena"; this arena is not
one -- `layInMemory` computes every global's offset from the whole module set,
so one more global moves the ones after it), and the **module initializer** is a
restart by name (a reload does not re-run it, so redirecting it would change
nothing while looking like it worked).

A second, independent check sits in `devhost.layRelay` and would catch a
classifier that let something through: the relayed image's `dataLen` and its
external list must equal the live image's, or the reload is refused with that as
the reason. The classifier argues from the source; this one argues from the two
images.

### 4. The frozen/reloadable policy and the generation counter

The policy is the classifier above, and the "reloadable set" is decided per
EDIT rather than per module: whatever changed and passed the test. The
indirection is installed lazily (step 4 of the reload), so nothing is frozen in
advance and a program that never reloads carries no slots at all. The counter is
`DevSession.generation`, and the guest reads it back from `devPoll()` -- which is
what lets the demo print it and a reader tell a reload from a restart.

### 5. The watcher

Modification times, polled, at `--dev-interval` (default 150 ms).
`lib/std/posix/kqueue.nim` is the event-driven answer and is in the tree, but it
is the **nimony** standard library: importable by a program nimony compiles, and
`nimony` itself is compiled by `nim c`. Polling is portable to all three hosts
for free and is far under a rebuild, so it is not what bounds the loop. The
watched set is every `.nim` file under the project file's directory minus the
nimcache; an edit to the standard library is not noticed, and the command says
what it is watching on startup rather than being quietly wrong about it.

### 6. The demo (`tests/dev/demo.nim`)

Written for this phase, because nothing in the tree could serve: `examples/`
holds one-shot scripts that run to completion. Single-threaded and long-lived,
with three procs that are three different cases on purpose -- `render` has
returned by the time the loop reaches its safepoint (so a body edit reloads),
`mainLoop` is ON the stack at the safepoint (so a body edit to it is deferred,
forever, and `nimony dev` says so and restarts), and `pause` is a leaf over one
external.

`{.noinline.}` on the reloadable procs is load-bearing and is the phase's one
user-visible constraint: an inlined proc has no entry to redirect, which is what
JIT.md 7.4 means by "safe: NON-INLINE body edits". Without it hexer splices
`render` into `mainLoop`, and the only thing that changed is the proc that is
live.

## The gate

> a demo application survives a body edit without restart, and restarts with a
> named reason on a signature edit.

`tests/dev/` drives it end to end: a real `nimony dev`, editing the real source
while the real program runs, reading the real stdout. Three edits, because two
cannot answer the question -- the third proves the RESTARTED guest is alive and
itself reloadable, which a run that ends the instant a restart is decided never
shows.

```
[dev] ok: the demo is running
[dev] ok: a body edit reloaded at tick 3 without restarting (the global counter kept going)
[dev] ok: the program's `devPoll()` reports generation 1
[dev] ok: a signature edit restarts, and says why: [dev] restart: the signature of render changed
[dev] ok: the restarted program starts over at tick 1 (the counter reset)
[dev] ok: the restarted program reloads too
[dev] ok: summary: [dev] done: 2 reload(s), 1 restart(s)
[dev] all checks passed
```

The reload's proof is not that the text changed; it is that the COUNT did not
reset. `ticks` is a global in the live data region, and a reload is exactly the
operation that leaves that region alone, so `tick N` followed by `TOCK N+1` is a
reload and `TOCK 1` would have been a restart wearing its coat. A longer manual
run makes the same point with more room:

```
tick 171 gen 0
TICK 172 gen 1
[dev] reloaded generation 1: render.0.demfu5gqa1
```

## One bug worth recording, because it cost an hour and is not obvious

`nimony dev` sets the `nimonyDev` define, which is what turns
`devreload.devPoll()` from a constant `0` into a call to the external the loader
answers. Setting it with `config.addDefine` in `dispatchBasicCommand` -- next to
`nimNativeAlloc` and `nimNativeIo`, which is where it looks like it belongs --
is **not enough**: that sets the define for the driver process, and the process
that sems the program is a child. The symptom is silent and looks like a
reloader bug: the program builds, runs, and never reaches a safepoint, so every
reload waits forever. It has to go into the forwarded arguments too
(`c.commandLineArgs.add " --define:nimonyDev"`), which is what `-d:nimonyDev` on
a command line does. The two native defines survive only because `deps` derives
them from `config.backend` independently.

## Not done, and what it would buy

* **The `(layouts …)` sidecar.** Would let a type edit that does not move an
  offset reload instead of restart. Not needed for soundness (above).
* **The signature/body split in `hexer/decldigest.nim`.** Would let the
  classifier read the sidecar the build already writes instead of walking every
  `.c.nif` per rebuild. That walk is fine for a demo and would matter for a
  large program.
* **An event-driven watcher.** kqueue/inotify/`ReadDirectoryChangesW`.
* **arm64 `getStackTrace`.** Out of B4 by decision: three intrinsic lowerings
  and a restructured seed, because `bl` leaves the return address in `lr` and an
  arm64 naked proc's SP therefore points at no slot. Recorded in JIT_IMPL.md's
  small-items list so the next person does not rediscover it.
* **JIT.md 7.3's build-time slot indirection** (an arkham `--reloadable` and a
  nifasm exclusion set). It would let a reload assemble ONE module instead of
  the whole program. On these numbers that is 0.09 s against 0.02 s, so it is an
  optimization, not the mechanism.
* **`--guest:subprocess` as the default for `nimony r`.** Kept off B4 by
  decision; it is a benchmark question on its own merits.
