M1 -- memory in the cost ledger and the scheduler
=================================================

branch:   jit/m1 (from fast-devloop 3bb7c4c3)
base:     f69b8afc (master fork point), /tmp/devloop_base
machine:  macOS 26.6.2 arm64, Apple M5 (10 cores), 16 GiB, Nim 2.2.10
backend:  native (`nimony n`)
method:   bench/devloop_ab.sh, A/B interleaved. A is always the fork point and
          is the drift control; B is this worktree. The machine was NOT quiet
          (other agents building in neighbouring worktrees), so the absolute
          wall times below drift between runs by up to 20 % and only the B/A
          ratio inside one run is a comparison.

          "The tip" is reproduced exactly by `NIMONY_INPROC_MEM_BUDGET=0`,
          which turns M1's rule off and leaves everything else identical. That
          is a better before/after than a second toolchain: one binary, one
          set of sources, one difference.

          uptime at the start of each block is recorded below.


1. The rule and its default
---------------------------

    decline in-process work when
        driverPeakNow + max(estimated rss of the depth's nodes) > budget

    budget = clamp(physicalMemory / (32 * cores), 128 MB, 1 GB)

`driverPeakNow` is `getrusage(RUSAGE_SELF).ru_maxrss` -- the peak so far, not
the resident size now. It is one syscall and it is monotone, and the reset
between in-process nodes drops the pools but not the pages, so the high-water
mark is the honest number for "what is this process still holding".

Overrides: `--inproc-mem-budget:MB`, `NIMONY_INPROC_MEM_BUDGET` (the
environment, so a nested `nimony s` inherits it), `0` to switch the rule off.
`--spawn:always` and `--vfs:disk` still force spawning as before.

On this machine the rule lands on its 128 MB floor. Why 32 and not 8 is a
measurement, not a derivation -- see block 3.


2. self.cold -- the headline
----------------------------

uptime 10:46, load 12.71 / 6.91 / 6.62 (busy; read the ratios, not the walls)
`bench/devloop_ab.sh /tmp/devloop_base . self.cold 3`, three rounds each.

| B side                              | wall  | cpu    | peak rss | B/A wall |
|-------------------------------------|-------|--------|----------|----------|
| M1 off (== the tip)                 | 6.108 | 13.735 | 218 MB   | 1.033    |
| M1 on, default budget (128 MB)      | 5.875 | 14.504 | **147 MB** | 0.979  |
| NIMONY_SPAWN=always                 | 6.363 | 15.358 | 147 MB   | 1.000    |
| A (fork point) in the same rounds   | 5.9-6.3 | 14.8-15.8 | 116 MB | --     |

    218 MB  ->  147 MB, which IS the spawn-always number.

147 MB is the floor the rule can reach at all: past that point the largest
process of the build is a CHILD (see block 4) and no decision the driver makes
about its own address space can shrink it.

Wall: 0.979 vs the tip's 1.033 against the same control in adjacent runs, i.e.
no cost, comfortably inside the 3 % gate. CPU is 5.6 % higher than with the
rule off, which is the fan-out the rule buys back -- and it is still 2.1 %
below the fork point's.


3. Why the divisor is 32 -- the budget sweep
--------------------------------------------

uptime 10:37-10:41, load 3.8-8.7. Two rounds each, same A control.

| budget          | peak rss | B/A wall |
|-----------------|----------|----------|
| off             | 217 MB   | 0.998    |
| 204 MB (= /8)   | 184 MB   | 0.970    |
| 160 MB          | 177 MB   | 0.960    |
| 128 MB (= floor)| 147 MB   | 0.980    |
| 100 MB          | 150 MB   | 0.979    |

None of them costs wall time, and below 128 MB nothing more is bought: 147 MB
is a child's peak. `physical / (8 * cores)` -- the first rule tried -- gives
204 MB here and stops 37 MB short of what is available for free. `/ 32` gives
53 MB, i.e. the 128 MB floor, which is where the value is. The divisor scales
the budget up only for machines with genuinely more memory per core (512 GiB /
64 cores -> 256 MB; 1 TiB / 16 cores -> the 1 GiB ceiling).

The self-tuning version of this constant is already in the ledger and is the
obvious follow-up: the driver has no business growing past
`max(entry.ewma.rssBytes)`, the largest peak any phase of THIS build was
measured at. It needs an answer for the first build on a fresh machine, which
is what this rule is.

The whole of the head's spawn-always 147 MB is ONE node: **dceLive**
(`hexer dl`, the whole-program live-set pass) at 146.7 MB. Everything else is
under 66 MB. `largest child 146.8 MB` -- `getrusage(RUSAGE_CHILDREN)` in the
driver -- confirms it from the other side and covers the three phases that
write no ledger fragment (`cc`, `arkham`, `link`).

The same two nodes measured at the fork point, run by hand under
`/usr/bin/time -l` out of its own `*.final.build.nif`:

    fork point  hexer dl (dceLive)   0.65 s   83.6 MB
    fork point  nifasm  (link)       1.11 s  122.2 MB

So:

* the fork point's largest process is the **link** (nifasm), 122 MB, which is
  the 116 MB the benchmark reports;
* `dceLive` went from **84 MB to 147 MB** and overtook it. That is P0c: the
  pass now builds and writes one `<M>.live.nif` per module -- 127 resolve
  subsets held at once -- instead of a single whole-program file. It bought
  126 dceEmit re-runs on an edit (progress.md P0c) and it cost 63 MB in the
  one process that does it.

That is the whole of the "+30 MB even when everything spawns": it is not
spread over the tools, it is `hexer dl`, and it is a known trade rather than a
leak. The cheap follow-up, if the 147 MB ever matters, is streaming the live
sets out per module instead of holding all of them.

The reason the edit loop cannot be disturbed is worth stating: its 112 MB peak

    [stats] driver peak 66.8 MB, largest child 146.8 MB

`*` marks a DRIVER peak: `nimsem` has only ever run inside this process here,
so 66.5 MB is the driver's high-water mark while it did, not nimsem's own
footprint (which the spawn-always table above puts at 54.5 MB). The two are
different measurements and the table says which is which rather than mixing
them.

The rule at work is visible in the two numbers at the bottom: the driver
stopped at 66.8 MB and `dceLive`, whose measured 146.7 MB cannot fit under a
128 MB budget however empty the driver is, spawned -- `spawn ms 0.0` in this
run is the ledger's memory of an earlier in-process run, not a claim that it
did not spawn.

Note that this holds with NO ledger at all: `self.cold` deletes the nimcache
every round, so `dceLive` estimates at its 64 MB default table entry and the
rule still declines once the driver has passed 64 MB doing nimsem and hexer
work -- which is exactly where the driver stops in the table above.


7. NIMONY_PROFILE_NODES=1
-------------------------

    [node] inproc nimsem sysvq0asl 0.0771 ready=1 rss=+15.3MB peak=19.9MB
    [node] inproc nimsem assy765wm 0.0021 ready=5 rss=+0.4MB peak=20.4MB
    [node] spawn  nifler paro2y9bh 0.0052 ready=165 childpeak=6.4MB

`rss=+N` is the growth of the driver's peak across the node -- what running it
here cost this process. `childpeak` is `RUSAGE_CHILDREN`'s running high-water
mark: one syscall, and honestly named, because it is the largest child so far
and not this one's own peak.


8. Overhead of the measurement itself
-------------------------------------

One `getrusage` per tool run (in `PhaseTimer.finish`, beside the fragment write
that was already there) and one per depth in the driver. Below the noise floor
of every scenario above; the `self.cold` cpu difference between M1 on and off
is the scheduler's fan-out, not the syscall.
