1. findTool and the current directory                       commit c363c449
----------------------------------------------------------------------------
Not a timing item: a build that failed.

Reproduction on 213b1a0b, from a scratch cwd that already holds a file
called `nimony` (the previous round's `--out:./nimony`):

  $ nimony c --spawn:always --nimcache:./nc --out:./nimony t.nim
  t.nim(4, 12) Error: cannot evaluate expression at compile time: f(13)
  /bin/sh: nimony: command not found
  FAILURE: .../bin/nifmake --base:'' --rerun -j run --progress:0:50 nc/tymsha01.build.nif

`findTool` began with `fileExists(name)` -- the cwd -- and returned the bare
name it matched, which a shell then resolves through PATH. Under the default
scheduler the CTFE sub-compile is in-process (A2c), so only `--spawn:always`
(and any build whose sem runs in its own process) reaches the shell with the
tool's name in it; that is the mode the failure was found in.

After: both rounds succeed and the program runs.

  $ nimony c --spawn:always --nimcache:./nc --out:./nimony t.nim   # twice
  $ ./nimony
  40

Test: `incrementalToolShadowTests` in src/hastur/incrementaltests.nim, called
twice from tests/incremental/setup.nim (default scheduler and
`--spawn:always`). Both rounds build from a fresh nimcache in a scratch cwd
with `--out:./nimony`, run the program, and assert the decoy was actually
written -- otherwise the second round would be testing nothing.

  tool-shadow: 2 / 2 phases successful in 1.81s.
  tool-shadow (--spawn:always): 2 / 2 phases successful in 2.51s.

Neutral. The finding is why: on this tip a DAG depth is never MIXED, so the
in-process nodes have no fan-out to overlap with. `NIMONY_PROFILE_NODES=1`
over a cold stdlib build (`nimony c`, node counts by depth):

  131 spawn nifler ready=134 + 3 spawn pluginbuild ready=134
    1 inproc nimsem ready=1
   22/7/9/14/9/20/3/2/3/4/6 spawn nimsem   (per depth, all spawned)
    1 inproc nimsem ready=1
   99 spawn hexer ready=99
    1 inproc dceLive ready=1
   99 inproc dceEmit ready=99
   99 spawn lengc ready=99
   99 spawn cc ready=99
    1 spawn link ready=1

Every depth holds one phase, and the rule decides per depth, so a depth is
either all in-process or all spawned. The in-process nodes run 3b attributed
0.1 s to are the `ready=1`/`ready=2` ones: on a warm forced stdlib build the
frontend graph reports 0.115 s in-process over 8 nodes at such depths and the
backend 0.033 s over 1. Nothing is beside them to hide that time behind.
Cross-depth pipelining (starting module M's `lengc` as soon as M's `dceEmit`
is done, rather than after all 99) is where that 0.1 s actually is; this item
is not that, and the serialization it names is gone either way.

Measured and rejected on the way: waiting on one live child unconditionally
(no `waitpid(-1)`, which would race with an in-process nimsem's sub-compile)
cost 11 % of stdlib.forced's wall -- 1.969 -> 2.188 s, cpu 9.183 -> 8.693 --
because the other job slots sat idle behind the slowest child. The shipped
`drain` polls on a 1 ms tick only while commands are still queued and blocks
exactly once the queue is empty.

`--report` byte-identical: nine reports over tests/incremental/sample.nim
(cold / no-change / forced, each under the default scheduler,
`--spawn:always` and `--vfs:memory+spill`) diff clean between A and B,
`inproc=` included.

Inside the dependency scan, before:

  frontend  nifler 1.35  processFileDeps 1.64  loadDepsFile 2.45 (247 files)
            resolveFile 1.31 (1259 calls)  toPair 21.19 (1596)  fileExists 0.60
  backend   loadDepsFile 1.22 (127 files)
            resolveFile 0.03 (1653)  toPair 11.69 (1781)  fileExists 0.90

So 32.9 of the 72 ms was `toPair` -> `moduleSuffix`: one `getCurrentDir` and
one `relativePath` per search path, per import, and the scan asks for the same
path once per module that imports it. Memoized in `DepContext.pairs`.

The other 9.6 ms was `openLedger` inside `installPhaseRelay`, folding ~700
fragments across 100 directories for a table whose only reader
(`depthWantsInproc`) a no-change build never reaches. `PhaseSchedule` now
holds the path and opens on first use.

Not worth cutting: the `.deps.nif` reads. `loadDepsFile` is 2.45 ms for 247
files (frontend) and 1.22 ms for 127 (backend); a cached digest would replace
3.7 ms with a stat sweep and a new staleness rule. Also measured: mmap vs read
for those files in isolation is 14.8 vs 7.1 ms per 298 files, but inside the
compiler the page cache is already warm and the whole line is 3.7 ms.

Build files are now emitted `OnlyIfChanged` (they are byte-identical on a
no-change run). It is a wash for time -- reading 112 KB + 262 KB back to
compare costs about what writing them did, 0.69 -> 0.65 and 1.54 -> 1.49 ms --
and is kept for the mtime: an unchanged graph now looks older rather than
newer, which is the safe direction for anything that compares against it.

What is left of the 35 ms: 20.2 ms of dependency scan (two passes, 254 + 127
`.deps.nif` parses and ~2900 import resolutions) and 13.4 ms of `runMake`
parsing two `.build.nif` files (112 KB + 262 KB), sorting them and asking
`needsRebuild` about every node.
