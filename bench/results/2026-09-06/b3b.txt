=============================================================

from `fast-devloop` at bad14fbf, i.e. everything through B3), nativenif pin

3. The premise: how many top-level declarations actually change
---------------------------------------------------------------

Every artifact of the sem module split into the children of its root
`(stmts ...)` -- the trailing embedded `(.index ...)` cut off at the byte
offset the header's `.indexat` names -- keyed by SymbolDef, compared by
content.  Three edit kinds, each measured from a warm tree:

  (a) in-place  one string literal in `checkExhaustiveness` made one
                character longer.  No line shift, no new declaration.
  (b) append    `proc devloopBenchBodyN(): int = 1` appended at EOF.  THIS
                IS `bench/devloop_bench.sh`'s `self.editbody`, i.e. the edit
                the phase's gate is stated on.
  (c) stmtadd   two statements inserted into an existing proc body at line
                2418 of 5610.  The typical real edit.

  artifact  decls |  (a) in-place |  (b) append  |  (c) stmtadd
  ----------------+--------------+--------------+--------------
  .s.nif    1228  |   1 changed  |  465 changed |  277 changed
  .x.nif    1759  |   1 (+1 -1)  |  464 (+1)    |  346 changed
  .c.nif     974  |   1 (+1 -1)  |  140 changed |  290 changed
  .asm.nif   975  |   1 (+1 -1)  |  140 changed |  248 changed

and the same comparison with NIF line-info tokens stripped before hashing:

  artifact  decls |  (a) in-place |  (b) append  |  (c) stmtadd
  ----------------+--------------+--------------+--------------
  .s.nif    1228  |   1          |  465         |   49
  .x.nif    1759  |   1          |  464         |   15
  .c.nif     974  |   1          |  140         |   15
  .asm.nif   975  |   1          |  140         |  248

Two upstream causes, BOTH outside `src/hexer/**`:

  * NIF LINE INFO.  Each top-level declaration anchors its own line info, so
    an edit that shifts line numbers rewrites the `@...` token of every
    declaration below it IN THE SAME FILE.  For (c) that is 277 of sem's
    1228 declarations; blind to line info it is 49.  Hexer can only work
    around this by rebasing the info tokens of every spliced fragment.

  * `sembasics.makeLocalSym` (src/nimony/sembasics.nim:450-456) numbers every
    LOCAL symbol from a module-wide per-name counter,
    `SemContext.locals: Table[string, int]` (src/nimony/semdata.nim:174).
    Insert or remove one local named `result` -- which every non-void proc
    has -- and every later `result.N` in the module is renumbered:
    `result.126` -> `result.127`, 465 of 1227 declarations for edit (b).
    Same for every other name shared across procs (`i`, `s`, `it`, `tmp`).
    Stripping line info does not help: these are genuine symbol renames that
    travel into `.dce.nif`'s `uses` sets and across modules.  Only
    `src/nimony/**` can fix it.

The `.dce.nif` was BYTE-IDENTICAL across edit (b), so step (3) of the phase
-- feeding the per-declaration diff into the `.dce.nif` analysis -- has
nothing to save on this workload.  `analyzeModule` is 5.8 ms of 244 anyway.


4. What that means for the gate
-------------------------------

Best case for the phase's OWN scenario (b), assuming a perfect,
byte-identical declaration-level hexer AND a perfect arkham splice:

  hexer   38 (I/O) + 36 (funcsummary + inliner) + 0.38 x 187   = 145 ms
          plus re-parsing the previous 7.1 MB `.x.nif`         = ~+25 ms
  arkham  ~45 (I/O) + 0.14 x 165                               =  ~68 ms
  ----------------------------------------------------------------------
  total                                                        ~238 ms

against 501 ms today: a real 2.1x, and still ABOVE the <= 0.2 s gate.
For the typical edit (c): ~120 ms hexer + ~90 ms arkham.
For edit (a): ~80 + ~50 ms -- but (a) is not a realistic edit.


5. arkham: does an unchanged proc's asm-NIF already match?
-----------------------------------------------------------

Cross-check per declaration: how many `.asm.nif` declarations changed whose
`.c.nif` INPUT declaration is byte-identical?  That is pure positional drift
inside arkham's own naming.

  edit (a) in-place : .c   3 changed -> .asm   3 changed -> drift   0
  edit (b) append   : .c 140 changed -> .asm 140 changed -> drift   0
  edit (c) stmtadd  : .c 290 changed -> .asm 248 changed -> drift 135

135 of 974 declarations get a different asm-NIF from an identical input.
The causes, all module-scoped in arkham at nativenif f8d2676:

  * `CodeGen.labelCount` (src/arkham/core/context.nim:146), consumed by
    `freshLabel` (x64/emit.nim:320, risc/emit.nim:1057) -> `L<N>.0`.  Reset
    per proc ONLY on AVR (avr/gen.nim:1358).
  * `CodeGen.rodata` (core/context.nim:130): a string literal is named
    `msg.<rodata.len>.<mod>` (x64/value.nim:815, risc/value.nim:1734), so the
    pool index of every later literal shifts.
  * temps named from the absolute token position in the INPUT module --
    `aggtmp<pos>`, `nctmp<pos>`, `botmp<pos>`, `rettmp<pos>`,
    `pairaddr<pos>`, `lvaltmp<pos>` -- shift when a preceding declaration
    changes token count.

So per-proc splicing of the previous `.asm.nif` is NOT byte-identical to a
full arkham run today, and what it would produce -- two procs both emitting
`L4856.0`, a stale `msg.7` pointing at a different string -- is a
correctness bug, not a cosmetic one.  Making `labelCount` and the rodata
index proc-scoped is the prerequisite, and it rewrites every `.asm.nif`
golden in nativenif.  No arkham change was made: the measurement says the
arkham half cannot be byte-identical without that prerequisite, and the
hexer half it is gated on does not land.

--------------------------------------------

  blobHits      3415
  blobStale       18

  blobResolve  137.16 ms
  blobRefs     143.32 ms

627 fragments re-recorded for a one-declaration change.  The blob cache's
UNIT is the symbol but its VALIDITY check is per module (`sameSource` on the
module's `.asm.nif` stamp, src/nifasm/blobcache.nim:449 and :752), so any

arkham's output per-declaration stable therefore buys nothing in nifasm
until that per-module check becomes per-symbol -- which is nifasm, B3c's
file, not this phase's.

9. Verdict
----------

Neither half of B3b is implemented, and the measurement is the reason.

  * The hexer half's premise -- "a body edit changes one top-level
    declaration" -- is false on this codebase: 38 % of sem's declarations
    change on the gate's own edit and 23 % on a typical two-line insertion,
    for two reasons that both live upstream of `src/hexer/**` (section 3).
  * Even with those fixed and a perfect implementation, section 4 puts
    hexer + arkham at ~238 ms on edit (b) -- above the <= 0.2 s gate.  The
    floor is set by 38 ms of unavoidable I/O on a 3.9 MB in / 7.1 MB out
    module plus 36 ms of whole-module analysis (funcsummary's fixpoint and
    the intra-module inliner) that no declaration-level diff can skip.
  * The arkham half cannot be byte-identical before `labelCount` and the
    rodata index are made proc-scoped (section 5), and would not reach
    nifasm's cache before its per-module validity check becomes per-symbol
    (section 6, B3c's file).

Ordered prerequisites, cheapest first:

  1. nimsem: `makeLocalSym` must number a local from its enclosing routine
     rather than from `SemContext.locals`, the module-wide per-name counter.
     Turns edit (b) from 465 changed declarations into ~1 and makes every
     `.s.nif` diff readable.  Small and self-contained; `src/nimony/**`.
  2. hexer: a line-info-blind declaration digest, plus an info REBASE for
     every spliced fragment.  Turns edit (c) from 277 into 49.
  3. hexer: per-declaration checkpoints for `EContext.tmpId`, `instId`,
     `localDeclCounters`, `strLitCounter`, `Pass.nextTemp`,
     `LiftingCtx.hookNames` and `InlinerCtx.counter`; per-declaration
     fragments for `c.initBody`, `c.pending`, `c.strLits`, `c.newTypes` and
     the lifted hooks; and an incremental `funcsummary` (its per-proc
     `ProcAnalysis` is cacheable -- only `resolveSummaries` +
     `annotateSummaries` must re-run).  This is the bulk of the work and
     where byte-identity is won or lost.
  4. arkham: proc-scoped `labelCount` and rodata index (rewrites every
     nativenif `.asm.nif` golden), then per-proc splicing.
  5. nifasm: per-symbol blob validity instead of per-module (B3c).

`tests/incremental` gained `incrementalDeclStabilityTests`, which pins the
declaration-stability numbers of section 3 on a small fixture so the premise
is a tracked regression rather than folklore, and fails if the churn grows.
