Phase P0c -- an edit re-emits only the modules whose live set changed
====================================================================

Machine: macOS 26, M5, 10 cores, Nim 2.2.10.  Branch `jit/p0c`, forked from
`fast-devloop` at acf637f6.  NIMONY_VFS=disk, EXTRA= (defaults: `--ctfe:auto`,
the in-process scheduler on).

The machine was NOT quiet: a sibling agent (A2c) was building throughout.
`uptime` is recorded beside every table.  That is why the headline number of
this file is the interleaved A/B in section 3 rather than the two absolute
tables in section 4: cpu-sum on `self.cold` drifts by ~1 s (4 %) between runs
taken minutes apart on this load, which is larger than anything P0c does to it.

134 executed commands -> 7.  `dceEmit` 127 -> 1, and `dceLive` does not run at
all: with `.dce.nif` now serialised in sorted order, the leaf module's analysis
is byte-identical and its `OnlyIfChanged` write preserves the mtime, so the
liveness phase is not even woken.  `cc` was 1 before and is 1 after -- the
`.c.nif` was already written `OnlyIfChanged`, which is JIT_IMPL.md P0c step 3
(verified, not changed).

The no-change build IMMEDIATELY AFTER that edit, which is the second half of
the problem (the 126 emits wrote nothing, so their `.c.nif` kept an mtime older
than the freshly written whole-program `.live.nif` and stayed stale forever):

    before:  nifmake-report total=0 inproc=0
             nifmake-report dceEmit=126 lengc=2 total=128 inproc=0
    after:   nifmake-report total=0 inproc=0
             nifmake-report lengc=2 total=2 inproc=0

(`lengc=2` is a pre-existing perpetual staleness of two lengc nodes and is
untouched by this phase.)


2. Correctness: the emitted Leng is unchanged
---------------------------------------------

A cold self-compilation with the P0c toolchain, compared file by file against
the one the pre-change toolchain produced from the same sources:

    identical=127 different=0

i.e. all 127 `.c.nif` files are byte-identical.  That is the empirical check on
`dce2.resolveKeysOf`, which gives each module's live file only the resolve
entries its own `.dce.nif` can justify instead of the whole table.

Sizes, same build:

    per-module live files: 127, 912211 bytes total, 7182 avg
    whole-program <main>.all.live.nif: 508151 bytes

Copying the whole resolve table (310336 bytes of the 508151) into each of the
127 files would have been 39 MB per build instead of 0.9 MB.

Also verified on the same build: the whole-program `.live.nif` before and after
a body-only edit had IDENTICAL SIZE and identical whitespace-split token
multisets (`tr -s ' ()\n' '\n' | sort | cmp` clean) -- it was a pure
permutation, produced by `HashSet[SymId]` iterating in hash order of a pool
index.  That is the root cause; see `notes/p0c.md` section 1.
